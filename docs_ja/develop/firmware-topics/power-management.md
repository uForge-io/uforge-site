# 電源管理 { #power-management }

電源管理によって、動作する試作機をウェアラブル向けの製品に仕上げます。SF32では、クロック設定、スリープモード、ディスプレイの動作、Bluetoothの接続間隔、センサー割り込み、アプリケーション構成が消費電力に影響します。

断片的なコードだけを見て消費電力を最適化しないでください。起動、アイドル、接続を維持したアイドル、ディスプレイ点灯、オーディオ動作、センサーによるウェイクアップ、OTA、シャットダウンなど、製品の動作シナリオを測定します。

## 実践ワークフロー { #practical-workflow }

1. 変更していないSDKサンプルの消費電力を測定します。
2. サブシステムを1つずつ有効にします。
3. 初期段階では、ディスプレイ、Bluetooth、オーディオ、ストレージ、センサーの動作を個別に測定します。
4. ポーリングの代わりに割り込みによるウェイクアップを使います。
5. 動作モードごと、製品シナリオごとの電流を記録します。

## 測定の出発点 { #useful-starting-points }

- SDKの電源管理サンプル。
- CPU使用率のプロファイリング。
- RT-Thread shellによる状態確認。
- ボード上での電流測定。

## 測定時の記録事項 { #measurement-notes }

各測定について、次の情報を記録します。

- ボードとリビジョン。
- 電源と測定箇所。
- ファームウェアのブランチとビルド。
- ディスプレイの状態。
- Bluetoothの状態。
- センサーの状態。
- ログ出力レベル。
- 平均電流、ピーク電流、測定区間。

## よくある電力問題 { #common-power-problems }

<div align="center"><em>表: よくある消費電力の問題</em></div>

<div align="center" markdown>

| 症状 | 考えられる原因 |
|:-----|:---------------|
| アイドル電流が高すぎる | ポーリングループ、ログ出力、ディスプレイ電源、周辺機器のクロックが有効なまま。 |
| スリープに入れない | 動作中のタイマー、開いたままのデバイス、処理待ちのタスク、未処理のウェイクアップ要因。 |
| Bluetoothの電流が急増する | 接続間隔、スキャンウィンドウ、オーディオ経路、再送。 |
| ディスプレイが消費電力の大部分を占める | LCDのバックライト消費電力、AMOLEDの表示内容、画面の更新方針、部分更新方式。 |
| 測定値のばらつきが大きい | 試験環境、バッテリー状態、USB電源経路、ログ負荷の変化。 |

</div>
