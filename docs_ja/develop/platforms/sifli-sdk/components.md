# コンポーネントと`sf-pkg` { #components-and-sf_pkg }

SiFliのプロジェクトでは、再利用可能なミドルウェア、ドライバー、コンポーネントがよく使われます。プロジェクトがサンプルの単純なコピーだけでは足りなくなったら、SiFliのパッケージ／コンポーネントの仕組みを使って、再利用可能なファームウェア部品を公開・管理します。

## コンポーネントの考え方 { #how-to-think-about-components }

複数の製品やサンプルで共有するコードには、コンポーネントを使います。

- 周辺機器ドライバー。
- ディスプレイパネルのサポート。
- Bluetoothサービス。
- GUIウィジェット。
- センサーアダプター。
- ストレージのヘルパー。
- 製品向けミドルウェア。

特定のアプリケーションだけで使うロジックは、インターフェースが安定し、複数のユーザーに利用されるようになるまでは、アプリケーションプロジェクト内に置いてください。

## 実践ワークフロー { #practical-workflow }

1. 動作するSDKサンプルから始めます。
2. 再利用対象とする部分を特定します。
3. 小さく、範囲の明確なAPIとして公開します。
4. SDK標準のビルド／設定機構を使って設定可能にします。
5. 依存関係、メモリー使用量、必要な周辺機器を文書化します。
6. その後で、再利用可能なコンポーネントとしてパッケージ化します。

## `sf-pkg`でコンポーネントを配布する { #use-sf-pkg-to-distribute-components }

コンポーネントは再利用可能な設計単位です。SiFliのコンポーネントレジストリはConanベースで、SDKの現在のコマンドラインサブコマンド名は`sf-pkg`です。

パッケージを利用するには、SDKプロジェクトの`project`ディレクトリで`sdk.py sf-pkg init`を実行し、`conanfile.py`を作成します。`requires`フィールドに`package/version@<username>`形式でパッケージ参照を追加します。`<username>`にはパッケージレジストリのユーザー名を指定してください。同じディレクトリで`sdk.py sf-pkg install`を実行します。インストールされたパッケージは`project/sf-pkgs`に配置され、そのKconfigファイルは`menuconfig`の`SiFli External Components`メニューに取り込まれます。

コンポーネントを公開するには、そのディレクトリで`sdk.py sf-pkg new --name <package_name>`を実行し、生成された`conanfile.py`を確認します。作成時に互換範囲を設定する場合は、`--support-sdk-version <sdk_version_range>`を追加できます。このオプションの有無にかかわらず、レシピの`support_sdk_version`に意図したSDKバージョン範囲が指定されていることを確認し、必要に応じて調整してください。パッケージにはセマンティックバージョニングを採用し、メタデータと依存関係を記述します。レジストリへの認証後、次のコマンドでビルドしてアップロードします。

```bash
sdk.py sf-pkg build --version <version>
sdk.py sf-pkg upload --name <package_name>/<version>@<username>
```

具体的な手順はSDKのバージョンによって異なる場合があります。環境設定、認証、バージョンごとのコマンドについては、SiFliの[パッケージ利用ガイド（中国語）](https://docs.sifli.com/projects/sdk/latest/sf32lb55x/sf_pkg/use.html)、[作成・公開ガイド（英語）](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/sf_pkg/create.html)、[中国語版](https://docs.sifli.com/projects/sdk/latest/sf32lb56x/sf_pkg/create.html)を参照してください。

## コンポーネントの品質基準 { #component-quality-bar }

次の条件を満たしたら、共有できるコンポーネントとみなせます。

- 環境と依存関係が文書化され、クリーンなチェックアウトからビルドできる。
- 最小構成のサンプルがある。
- 必要な設定が文書化されている。
- 隠れたボード依存がない。
- エラーを明確に報告する。
- グローバルリソースを使う場合は、その所有権と解放規則を明記する。
- スレッド、コールバック、メモリーの所有権に関する規則が明示されている。

## 記録する内容 { #what-to-record }

再利用可能な各コンポーネントには、次の情報を記載してください。

- 対応チップとボード。
- 必要なSDKバージョン。
- 必要な周辺機器とピン。
- RTOS／ミドルウェアの必須設定。
- スレッドとコールバックの動作。
- RAM、Flash、スタックの見込み使用量。
- サンプルプロジェクトのパス。

## よくある落とし穴 { #avoid-these-traps }

<div align="center"><em>表: 避けるべき落とし穴</em></div>

<div align="center" markdown>

| 落とし穴 | より良い方法 |
|:---------|:-------------|
| 各製品にサンプル全体をコピーする。 | 安定して再利用できる層だけを切り出す。 |
| コンポーネントのコードにピン名を埋め込む。 | 設定経由でボードのリソースを渡す。 |
| ディスプレイ／オーディオ経路が1種類だけだと想定する。 | 対応するハードウェア経路を文書化する。 |
| メモリー使用量を無視する。 | スタック、ヒープ、DMA、バッファーの要件を記録する。 |
| サンプルなしでリリースする。 | 最小構成の統合サンプルを1つ含める。 |

</div>
