# デバッグと診断 { #debugging-and-diagnostics }

SF32 のデバッグはシリアルログから始めます。チップ、SDK リリース、プロジェクト設定によっては、クラッシュダンプ、トレース取得、RT-Thread シェルも利用できます。対象向けに文書化された手順だけを使用してください。

## 最初に行う確認 { #first-line-debugging }

シリアルコンソールから次の情報を取得します。

- 起動ログ。
- アプリケーションの出力。
- RT-Thread シェルの出力（プロジェクトで有効な場合）。
- 異常メッセージ。
- ダウンロードとリセットの動作。

ログには、ボードリビジョン、SDK ブランチ、ビルドコマンド、書き込みコマンド、シリアル設定を添えて保管してください。

## デバッグの順序 { #debugging-order }

1. 同じファームウェアで現象を再現します。
2. リセット後に再現するか確認します。
3. ファームウェア全体を書き込み直した後に再現するか確認します。
4. 最も近い SDK サンプルで再現するか確認します。
5. 製品固有の変更を 1 つずつ戻して追加します。

この順序により、ハードウェア、ボードサポート、ミドルウェア、アプリケーションの問題を切り分けやすくなります。

## 知っておきたいツール { #tools-to-know }

<div align="center"><em>表: 知っておきたいツール</em></div>

<div align="center" markdown>

| ツール | 用途 |
|:-------|:-----|
| `sftool` | 対応するチップ／ストレージに対する Flash の読み書き・消去やリセットを行うシリアル CLI。オプションはチップとストレージの種類によって異なります。 |
| `SiFli_Trace` | 対象でサポートされる手順に従ってボードのログを取得・確認します。 |
| `UsartServer` | SF32LB52X と SF32LB56X で内蔵 Debug IP を UART 経由でデバッグする際に必要な補助ツールです。他の対象にも適用できるとは限りません。 |
| `AssertDump` とクラッシュダンプツール | 対象チップと SDK リリースで提供される場合のみ使用し、その版の取得・解析手順に従います。 |
| RT-Thread シェル | プロジェクト設定で有効な場合に限り、実行時の確認やコマンド実行に使用できます。 |

</div>

## 最初に確認する項目 { #what-to-inspect-first }

<div align="center"><em>表: 最初に確認する項目</em></div>

<div align="center" markdown>

| 症状 | 最初に確認する項目 |
|:-----|:-------------------|
| HardFault またはアサーション | スタックサイズ、null ポインター、DMA バッファー、キャッシュのメンテナンス。 |
| 周辺機器が応答しない | ピン多重化、クロック、電源レール、ボード名、ドライバーの有効化。 |
| Bluetooth が不安定 | RF クロック、アンテナ経路、Bluetooth スタックの設定、接続パラメーター。 |
| ディスプレイに表示乱れがある | パネルのタイミング、バッファー形式、キャッシュ／DMA 同期。 |
| ランダムにリセットする | ウォッチドッグ、電源レール、電圧低下（ブラウンアウト）、スタックオーバーフロー。 |

</div>

## クラッシュレポートのチェックリスト { #crash-report-checklist }

クラッシュを報告する際は、次の情報を含めてください。

- ボードとリビジョン。
- チップのバリアント。
- SDK ブランチまたはコミット。
- 対象のサンプルまたはプロジェクト。
- ビルドコマンドとボード名。
- Flash 書き込みコマンド。
- リセット直後からのシリアル起動ログ。
- クラッシュダンプまたはアサーション出力。
- 変更していない SDK サンプルでも問題を再現するかどうか。
