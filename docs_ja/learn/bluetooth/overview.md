# Bluetooth概要 { #bluetooth-overview }

## 概要 { #overview }

このガイドでは、SF32製品のBluetooth接続をどのように計画・実装するかを説明します。BLEとデュアルモードBluetoothの選択、GATTサービス設計、プロファイル選定、接続パラメータの調整、ペアリングとセキュリティ、LE Audio、グラフィックス・オーディオ・センサーの各処理との共存など、実際の設計で必要となる判断を中心に扱います。

SF32は、アプリケーション処理と厳密なタイミングを要するBluetoothコントローラ処理を分担します。通常、製品ロジックとUIはアプリケーションプロセッサが実行し、リンクレイヤのタイミングと無線スケジューリングはBluetoothプロセッサまたは低消費電力プロセッサが担当します。ホストスタックとGATTサービスの実行先は、デバイスとSDK構成によって異なります。すべてのサービスがアプリケーションプロセッサで動くとは想定せず、選んだサンプルのコア構成とコア間通信を確認してください。

基盤となるサブシステムのより詳細な説明については、[Bluetoothプロセッサアーキテクチャ](processor.md)を参照してください。

製品に必要なロールとプロファイル、ユーザーが期待する応答性とバッテリー寿命、スマートフォン・無線部・アプリケーションファームウェアの役割分担を定義する際に、このページを参照してください。本ページは設計ガイドであり、対象のスマートフォンやアクセサリを使った相互運用性の検証に代わるものではありません。

## 製品の無線接続要件を定義する { #define-the-products-connectivity-requirements }

GATTのコードを書く前に、製品が実際に何を必要とするかを明確にしてください。

- BLEのみか、デュアルモードBluetooth（BT Classic + BLE）か。
- BluetoothオーディオはClassic（A2DP/AVRCP/HFP）か、それともLE Audioか。
- 一般的な接続間隔、レイテンシ、スループットの要件。
- アプリケーションプロセッサをどの程度の頻度でスリープから復帰させる必要があり、どのくらいスリープ状態を維持できるか。
- 製品が既存のスマートフォン側のサービス（通知、メディア制御、通話）と相互運用する必要があるか、それともカスタムのコンパニオンアプリのみか。
- 想定される到達距離、アンテナ/筐体の制約、RF認証の目標。
- ファームウェア更新をBluetooth経由で配信するかどうか。

これらの要件に基づいて、デバイスと出発点となるSDKサンプルを選び、メインCPUをスリープ状態に維持できる時間を判断します。

## BLE、Classic、デュアルモードを選ぶ { #choose-ble-classic-or-dual-mode }

### Bluetooth Low Energy（BLE） { #bluetooth-low-energy-ble }

BLEは、ほとんどの接続型ウェアラブルやセンサーにとって適切なデフォルトです。断続的でイベント駆動のトラフィック、低い平均消費電力、幅広いスマートフォンOSサポートを備えています。BLE優先の代表的な製品には、フィットネスバンド、健康センサー、ビーコン、コンパニオンアプリへの構成/制御リンクがあります。

### Classic Bluetoothとデュアルモード { #classic-bluetooth-and-dual-mode }

製品にオーディオストリーミング（A2DP/AVRCP）、ハンズフリー通話（HFP）、シリアル形式のデータリンク（SPP）、または既存のClassicプロファイルとの互換性が必要なら、Classic Bluetoothを追加します。デュアルモードでは、BLE専用の場合より無線スケジューリングと共存の要件が厳しくなります。専用Bluetoothプロセッサは、こうした無線処理の負荷をシステムの他の処理から切り離すために用意されています。

すべてのSF32製品がデュアルモードBluetoothに対応しているわけではありません。型番を決める前に、[Bluetoothプロセッサアーキテクチャ](processor.md#device-family-differences)のデバイス表を確認してください。

## GATTサービスとSiblesフレームワーク { #gatt-services-and-the-sibles-framework }

SiFli-SDKでは、**Sibles**を使ってGATTサービスを登録・利用します。GATTはサービス/キャラクタリスティックの階層構造と属性へのアクセス方法を定義し、GAPはデバイスの発見・アドバタイズ、接続の確立、および各ロールを扱います。両者は役割を分担しており、GATTがGAPの上に実装されるという意味ではありません。GATTデータベースを一から作るより、要件に近いSDKサンプルを出発点にしてください。

SDKには、標準およびベンダー独自の複数のプロファイルのサンプル実装が同梱されています。

<div align="center"><em>表: GATTサービスとSiblesフレームワーク</em></div>

<div align="center" markdown>

| プロファイル/サービス | 一般的な用途 |
|:-------------------|:------------|
| **HRPC**（心拍数プロファイルのコレクター） | GATTクライアントとして外部センサーの心拍数を受信する。フィットネスや健康モニタリング製品向け。 |
| **DISS**（デバイス情報サービス） | メーカー、モデル、ファームウェアバージョンをスマートフォンに公開する。 |
| **CTS**（現在時刻サービス） | スマートフォンからデバイスへの時刻同期。 |
| **BASC** / **CSCPC** / **CPPC** | フィットネス用途向けの、バッテリー、サイクリング速度/ケイデンス、サイクリングパワーのコレクタプロファイル。 |
| **HID over GATT** | キーボード、リモコン、その他の入力デバイスのエミュレーション。 |
| **ANCS**（Apple Notification Center Service）クライアント | デバイス上でiOSの通知を読み取る。 |
| **AMS**（Apple Media Service）クライアント | デバイスからiOSのメディア再生を制御する。 |
| シリアル転送プロファイル | 機能面ではSPPに近い、BLEのGATT経由で行うカスタム双方向データ転送。 |

</div>

近い用途のサンプルから、登録処理、イベント処理、セキュリティチェックを再利用してください。標準プロファイルを実装する場合は、標準のUUIDと規定動作を維持します。製品のデータモデルに必要なら、独自のサービスとUUIDを設計して構いません。目的は検証済みの基盤処理を再利用することであり、すべてのアプリ連携を標準プロファイルに無理に当てはめることではありません。

## Classic Bluetoothプロファイル { #classic-bluetooth-profiles }

デュアルモード製品向けに、SDKは以下のサンプルプロファイル実装を提供します。

- **SPP** — シンプルな双方向シリアルデータ。レガシーまたは非GATTのコンパニオンアプリに有用。
- **A2DP**（シンクおよびソース） — Bluetoothオーディオストリーミング。
- **AVRCP** — A2DPリンクと併せた再生制御（再生/一時停止/トラック/音量）。
- **HFP**：ハンズフリー通話。HF（ハンズフリー機器）とAG（オーディオゲートウェイ）の役割があります。ドキュメントに掲載された[HFPサンプル](https://docs.sifli.com/projects/sdk/latest/sf32lb58x/example/bt/hfp/README.html)はHFを実装しています。AGの対応は、選択したSDK構成で別途確認してください。
- **PAN** — Bluetooth経由のネットワーク。PANベースのOTA配信例を含む。

オーディオや従来型のプロファイルは、一般的なBLE接続よりタイミングとスループットの要件が厳しい傾向があります。共存テストにも十分な時間を確保してください（下記の[他のワークロードとの共存](#coexistence-with-other-workloads)を参照）。

## BluetoothオーディオとLE Audio { #bluetooth-audio-and-le-audio }

オーディオへのアプローチに応じて、2つの異なるパスがあります。

- **Classic Bluetoothオーディオ** — ストリーミング用のA2DP、再生操作用のAVRCP、通話用のHFP。成熟しており、既存のスマートフォンやヘッドセットと広く互換性があります。
- **LE Audio** — [Basic Audio Profile（BAP）](https://www.bluetooth.com/specifications/specs/basic-audio-profile-1-0-2/)は、ユニキャストとブロードキャストの両方のLE Audioストリームを管理する手順を定義しています。SDKにはブロードキャストソースとシンクの例があり、移行期間中にClassic BTとLE Audioを併用する製品向けの、両方式を組み合わせたブロードキャストソースの例も用意されています。

どちらの方式でも、安定したタイミング、バッファリング、音声サンプルの確実な転送が必要で、通常はDMAを使います。必要なBluetoothオーディオの役割とSDK構成に対応するかを確認して、SF32LB52x/56x/58xを選んでください。SF32LB55xはBLE専用でClassic Bluetoothオーディオには対応しませんが、ローカル音声機能がないという意味ではありません。DMAとバッファリングについては、[オーディオ概要](../audio/overview.md)と[Bluetoothプロセッサアーキテクチャ](processor.md#bluetooth-audio-and-le-audio)を参照してください。

## Siblesサービスの実装パターン { #implementation-pattern-for-sibles-services }

保守可能なBLEサービスは、通常次のパターンに従います。

<div align="center"><em>表: Siblesサービスの実装パターン</em></div>

<div align="center" markdown>

| ステップ | ファームウェアの責務 | レビューすべきポイント |
|:-----|:------------------------|:-------------|
| サービス仕様を定義する | UUID、キャラクタリスティック、パーミッション、通知の挙動。 | コンパニオンアプリとセキュリティ要件に合わせる。 |
| サービスを登録する | 要件に最も近いSDKサンプルが使うSibles/GATTの実装方法に従う。 | 独自のサービス登録処理を場当たり的に追加しない。 |
| 必要な情報に絞ってアドバタイズする | 発見と再接続に必要なデータのみを含める。 | アドバタイズペイロードを小さく安定させる。 |
| 書き込みを検証する | 長さ、状態、権限、コマンドシーケンスを検証する。 | 不正なアプリ通信によるファームウェアの不安定化を防ぐ。 |
| 通知を必要最小限にする | 同じ状態を繰り返し通知せず、変更分やまとめたデータを送信する。 | 無線の占有時間とアイドル時の消費電力を抑える。 |
| 状態を保存する | ボンディング鍵と製品設定を安全に保存する。CCCDの購読状態はクライアントごとに管理し、ボンディング済みなら接続をまたいで保持し、未ボンディングなら接続ごとに既定値へ戻す。 | 再起動・OTA後の復旧を検証する。GATTデータベースの変更に対応し、古いハンドルをそのまま復元しない。 |

</div>

こうすることで、サービス定義、スマートフォンアプリとのインターフェース、セキュリティポリシー、電力特性を整合させられます。

## アドバタイズと接続パラメータ { #advertising-and-connection-parameters }

接続パラメータとアドバタイズパラメータは、レイテンシ、スループット、消費電力のバランスを調整する主な項目です。

これらはBLE ACLリンクの接続パラメータであり、すべてのBluetooth音声転送に適用されるわけではありません。Classic Bluetooth音声はBR/EDRの転送タイミング、LE AudioはCISまたはBISのアイソクロナス転送タイミングを使います。BLE GATTの接続間隔を、そのまま両方式の音声経路に適用しないでください。各転送方式の違いは[Bluetooth SIGのLE入門資料](https://www.bluetooth.com/bluetooth-le-primer/)で説明されています。

<div align="center"><em>表: アドバタイズと接続パラメータ</em></div>

<div align="center" markdown>

| パラメータ | 効果 | ガイダンス |
|:----------|:-------|:---------|
| アドバタイズ間隔 | 検出速度とアドバタイズ時の消費電力 | 速やかな検出が必要な期間だけ短くし、その後は接続や再接続を待つ間隔を長くする。接続済みであること自体は、アドバタイズの継続を必要としない。 |
| 接続間隔 | BLE ACLの応答時間と消費電力 | 通信量が少ないリンクでは、長い間隔で平均消費電力を抑えられる。短い間隔は操作への応答を改善できる。対象スマートフォンで、実際に合意された設定、スループット、電流を確認する。 |
| ペリフェラルレイテンシ（旧SDKではSlave Latency） | ペリフェラルが接続イベントをスキップできるようにする | ほとんどアイドル状態のリンクではバッテリー寿命を延ばす。低消費電力よりも低レイテンシが重要な場合は0に設定する。 |
| スーパービジョンタイムアウト | 有効なリンクレイヤのデータパケットを受信せずに、リンク喪失と判定するまでの最大時間 | 短すぎるとRF環境が不安定な場合に切断が増える。長すぎると実際に切断した後の再接続が遅れる。 |
| 送信電力 | 通信距離、消費電力、共存性のバランス | 必要な通信距離を満たす最低の設定から評価する。最終筐体で総消費エネルギー、再送、他の無線との共存を測定する。低い設定で再送が増える場合、最低設定が最も省電力とは限らない。 |

</div>

ビーコン形式の製品（iBeacon互換のアドバタイズ）や、周期的アドバタイズのユースケース（大規模または単方向ブロードキャスト向けの周期的アドバタイズ同期を含む）は、完全なGATT接続を必要とせず、専用のSDK例を通じてサポートされています。

接続間隔、ペリフェラルレイテンシ、スーパービジョンタイムアウトは、コントローラと相手機器が受け入れられる有効な組み合わせにする必要があります。更新を要求しただけでは、設定が反映されたとは限りません。実際に合意された値を記録し、要求の拒否やアイドル時の省電力設定への復帰も含めて、対象のスマートフォンや周辺機器で検証してください。

## 製品フェーズごとのパラメータプリセット { #parameter-presets-by-product-phase }

すべてのフェーズで単一の折衷設定を使うのではなく、フェーズごとに適切なBluetoothパラメータを設定してください。

<div align="center"><em>表: 製品フェーズごとのパラメータプリセット</em></div>

<div align="center" markdown>

| フェーズ | 一般的な目標 | 設定の目安 |
|:------|:-------------|:--------------------|
| 初回のデバイス検出 | すばやく見つけられること | 短いアドバタイズ間隔、明確なデバイス識別情報、アドバタイズ時間の制限。 |
| 再接続 | 平均消費電力の低減 | タイムアウト後はアドバタイズ間隔を長くする。適切な場合は対象を絞った方式やフィルタリングを使う。 |
| インタラクティブ制御 | 低レイテンシ | より短い接続間隔、低いまたはゼロのペリフェラルレイテンシ。 |
| 接続済みアイドル | バッテリー寿命 | より長い接続間隔、非ゼロのペリフェラルレイテンシ、最小限の通知。 |
| BLE OTA転送 | スループットと信頼性 | 短い間隔、ペリフェラルレイテンシなし、保守的なスーパービジョンタイムアウト。 |
| オーディオ | 安定したタイミング | コーデックのフレームタイミングとバッファ深度を中心に選ばれたパラメータ。 |

</div>

フェーズ間の遷移条件を文書化してください。「ランダムに見える」Bluetoothの消費電力やレイテンシの問題は、状態が変わった後も製品が誤ったフェーズに留まっていることが原因の場合があります。

## ペアリング、ボンディング、セキュリティ { #pairing-bonding-and-security }

BLEはペアリングなしでも接続できます。ペアリングではセキュリティ鍵を生成し、ボンディングでは後の接続で再利用するために鍵を保存します。すべての製品にボンディングが必要と決めつけず、各サービスに必要な暗号化、認証、鍵の永続保存を判断してください。

- Just Works、パスキー入力、数値比較のどのペアリング方式が必要かを早期に決めてください。Just Worksは中間者攻撃（MITM）を防ぎません。暗号化された接続でも、認証済みとは限りません。両機器のI/O能力と製品のセキュリティ要件に合う方式を選んでください。[Bluetooth GAPのセキュリティ要件](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-60/out/en/host/generic-access-profile.html)も参照してください。
- [ANCS](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleNotificationCenterServiceSpecification/Specification/Specification.html)では、スマートフォン側の利用許可と、リンクの暗号化やボンディングは別の条件です。許可の拒否や取り消しに対応してください。ANCSと[AMS](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleMediaService_Reference/Specification/Specification.html)は接続中に公開・非公開が切り替わる場合があります。Service Changedを監視してサービスを再探索し、ペアリング後も常に利用できるとは想定しないでください。
- SDKが推奨するストレージ/パーティション方式に従ってボンディング情報を保存し、再起動やOTA更新後も保持できるようにしてください。
- 製品のUI側とスマートフォン側の両方に、再ペアリングと「デバイスを忘れる」フローを定義してください。
- セキュリティポリシー（暗号化要件、I/O能力、鍵サイズ）は、検討せずに放置するデフォルトではなく、製品としての判断として扱ってください。

## マルチ接続とロール { #multi-connection-and-roles }

SDKには、**セントラルとペリフェラルの同時動作**と**複数の同時接続**のサンプルがあります。スマートフォンにはBLEペリフェラルとして接続し、センサーにはセントラルとして接続する製品や、複数の相手機器と接続する製品で利用できます。役割の組み合わせと接続数の上限は、デバイス、コントローラファームウェア、SDK構成、バッファ、無線処理の総負荷に応じて確認してください。サンプルの動作は、全シリーズで同じ接続容量が保証されることを意味しません。

リンクのスループットを上限近くまで高めたい場合は、制限がアプリケーションコードにあると決めつける前に、SDKのスループットサンプルを基準として試してください。

## Bluetooth経由のOTAファームウェア更新 { #ota-firmware-updates-over-bluetooth }

一般的な配信パスは2つあります。

- **BLE経由のDFU形式の更新**。ペリフェラル接続と統合されています（通常のペリフェラルGATTロールにOTAがどのように組み込まれるかについては、`peripheral_with_ota`の例を参照）。
- **PAN OTA**。データ用にすでにPANを使用しているデュアルモード製品向けに、Bluetooth PANネットワークリンク経由でファームウェアを配信します。

どちらの方式でも、出荷前にパーティション構成、障害復旧、ロールバックを計画し、検証してください。BLE OTAでは、転送中の接続間隔を短くし、ペリフェラルレイテンシを0にする設定を評価し、転送後に通常の省電力設定へ戻します。PAN OTAはClassic Bluetoothによる転送です。BLEの接続パラメータを流用せず、スループットと復旧方法を別途調整してください。

## 他のワークロードとの共存 { #coexistence-with-other-workloads }

SF32上のBluetoothが単独で動作することはほとんどありません — グラフィックス、オーディオ、センサー、そして時には外部Wi-Fiとシステムを共有します。専用のBluetoothプロセッサが時間制約の厳しいリンク処理の大部分を担いますが、アプリケーションレベルの共存には引き続き注意が必要です。

- アプリケーションプロセッサ上の長いクリティカルセクションや割り込みの無効化は、ホスト側のBluetooth処理を遅らせる可能性があります。
- ディスプレイとPSRAMのトラフィックは、Bluetoothオーディオバッファとメモリ帯域幅を奪い合います。
- センサー割り込みがアプリケーションプロセッサを頻繁に起こすと、Bluetoothプロセッサがリンク処理を担う間、アプリケーションプロセッサをスリープさせておけるという省電力効果が失われます。

システムレベルの説明は[他のワークロードとの共存](processor.md#coexistence-with-other-workloads)を参照してください。各サブシステムを単独で試すだけでなく、ディスプレイとオーディオを動作させながらBLEリンクにも負荷をかけるなど、実際に起こり得る厳しい組み合わせで検証してください。

## RF、相互運用性、認証への準備 { #rf-interoperability-and-certification-readiness }

Bluetoothファームウェアは、RFハードウェアと同じ厳格さで検証されるべきです。

- 1台の開発用スマートフォンだけでなく、複数のスマートフォンベンダー、OSバージョン、再接続シナリオでテストしてください。
- 古いボンド、スマートフォン側のデバイス削除、デバイス側の工場出荷時リセット、OTAの後の挙動を確認してください。
- バッテリー、ディスプレイ、充電器、ユーザーが装着/保持する位置とともに、最終的な筐体で到達距離とパケットの安定性を検証してください。
- 量産と認証サポートのために、RFテストモード、較正アクセス、ログを利用可能な状態に保ってください。
- プロファイルの多い製品では、認証/プロファイルテストの時間を確保してください。デモアプリが動作することは、相互運用可能であることと同じではありません。

## よくある間違い { #common-mistakes }

- 製品がすでにClassicオーディオを必要としているのに、BLE専用のハードウェアを選んでしまう。
- サービスの基盤処理を不要に作り直したり、独自データモデルを不適切な標準プロファイルに当てはめたりする。
- ほとんどの時間をアイドルで過ごすリンクで、ペリフェラルレイテンシを0のままにしてしまう。
- ディスプレイ/オーディオ/Bluetoothが初めて組み合わされる、統合の終盤まで共存テストを怠ってしまう。
- ペアリング/ボンディングを、設計されたUXフローではなく後回しの検討事項として扱ってしまう。
- 最終的なPCBリビジョンまで、RF立ち上げ検証（アンテナ、マッチングネットワーク、クリスタルの精度）を省いてしまう。
- ファームウェアだけのチューニングで、貧弱なRFレイアウトを補えると想定してしまう。

## 立ち上げチェックリスト { #bring-up-checklist }

- [ ] BLE専用かデュアルモードかの要件を確認し、それに合ったSF32デバイスを選定する。
- [ ] 製品のユースケースに最も近いSDKのプロファイル/サービス例を特定する。
- [ ] 発見、アクティブな利用、アイドル状態のためのアドバタイズおよび接続パラメータの目標を定義する。
- [ ] ペアリング、ボンディング、「デバイスを忘れる」UXを設計する。
- [ ] 実際のハードウェアでRFレイアウト、アンテナマッチング、クリスタルの精度を検証する。
- [ ] 選定したプロファイル（GATTサービス、A2DP/AVRCP/HFP、またはLE Audioブロードキャスト）を実際のスマートフォンまたはリファレンスホストに対して立ち上げる。
- [ ] 現実的な組み合わせ負荷の下で、ディスプレイ、オーディオ、センサーのワークロードとの共存をテストする。
- [ ] ファームウェア更新をBluetooth経由で配信する場合は、OTA配信パスを計画・テストする。
- [ ] 接続アイドル時の消費電力を測定し、アプリケーションプロセッサが想定どおりにスリープすることを確認する。

## 要点のまとめ { #key-takeaways }

- まずBLE専用かデュアルモードBluetoothかを決めてください。これがデバイス選定と、その後のSDK開発方針を大きく左右します。
- ゼロから構築するのではなく、SDKの既存のGATTサービスとClassicプロファイルの例（HRPC、DISS、CTS、HID、ANCS/AMS、SPP、A2DP、AVRCP、HFP、PAN）から始めてください。
- 接続間隔、ペリフェラルレイテンシ、スーパービジョンタイムアウト、送信電力が、レイテンシ、スループット、消費電力のバランスを取る主な調整項目です。
- Bluetooth音声では、選択したデバイスとSDK構成が必要なClassic BluetoothまたはLE Audioの役割に対応するか確認し、バッファリングと共存を設計・検証してください。ファミリー全体の機能説明だけでは判断できません。
- Bluetoothはシステムレベルの関心事です。RFレイアウト、クロック、ペアリングUX、グラフィックス/オーディオ/センサーとの共存は、GATTコード自体と同じくらい重要です。

現行のClassic Bluetooth、BLE、LE AudioのSDKプロジェクトを開発タスク別に整理した一覧については、[Bluetooth SDKの例](bluetooth-sdk-examples.md)を参照してください。

対象デバイスの実際のBluetooth消費電力を測定・分析する実践的な方法については、[Bluetoothの消費電力を測定・分析する](bluetooth-low-power-profiling.md)を参照してください。
