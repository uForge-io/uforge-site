# Bluetoothプロセッサ { #bluetooth-processor }

## はじめに { #introduction }

**Bluetoothプロセッサ**は、SF32LBデバイスに搭載された無線制御専用のサブシステムです。無線通信のスケジューリング、リンク制御、低消費電力での接続維持、メインのアプリケーションプロセッサとの連携など、厳密なタイミング制御が必要なBluetooth処理を担います。

この構成は、バッテリー駆動のネットワーク対応製品に有効です。SF32は異種マルチコア構成で処理を分担するため、無線イベントごとにメインのアプリケーションCPUを起動する必要はありません。アプリケーションプロセッサが製品ロジックとユーザー向け機能を担い、低消費電力のBluetoothプロセッサまたは常時動作プロセッサが無線リンクを維持します。

低消費電力プロセッサでアプリケーションコードを実行できる範囲は、シリーズによって異なります。下の比較を参照し、対象品種とSDKで利用できるタスク配置を検証してください。

このページでは、Bluetoothのタイミング制御やコントローラファームウェアの実行場所、選定した品種の低消費電力コアをプログラムできるかどうか、アプリケーションCPUを休止させながら接続を維持する方法を説明します。サービスの設計や製品へのBluetooth統合については、[Bluetooth概要](overview.md)を参照してください。

## 専用Bluetoothプロセッサが重要な理由 { #why-a-dedicated-bluetooth-processor-matters }

Bluetoothは、必要なときだけバックグラウンドで動く単純なソフトウェアプロトコルではありません。接続機器は、アドバタイズ、スキャン、接続イベント、パケット交換、音声伝送、暗号化、ほかのシステム処理との共存において、厳密な無線時間要件を満たす必要があります。

専用のBluetoothサブシステムは、時間制約の厳しい無線処理をアプリケーションの主な処理から分離します。これにより、次のような利点が得られます。

- 接続済みスタンバイ中の平均消費電力の低減。
- UI、グラフィックス、オーディオ、AIの処理が重い場合でも、無線通信のタイミングを安定して維持できる。
- コントローラ側の無線イベントを、毎回アプリケーションCPUを起動せずに処理できる。
- アプリケーションファームウェアとプロトコル制御ファームウェアのより明確な分離。
- メインCPUが休止している間も接続を維持する製品を実現しやすい。

ウェアラブルや携帯機器では、この分離が特に有効です。製品の稼働時間の大半を低消費電力の接続状態で過ごし、ユーザー操作、センサーイベント、画面更新、音声処理、スマートフォンとの同期が必要なときだけ起動できます。

これらは設計上の利点であり、特定の消費電力や復帰時間を保証するものではありません。ホストスタックの実行場所、割り込み、クロックの起動、スリープ方針、アプリケーション通信量によって実測値は変わります。対象のファームウェアと処理負荷で、電流と応答時間を測定してください。

## SF32システムにおける位置づけ { #position-in-the-sf32-system }

簡略化したSF32の無線アーキテクチャは次のようになります。

<div align="center"><em>図: SF32の無線アーキテクチャ（簡略図）</em></div>

```text
アプリケーションプロセッサ
  - 製品ファームウェア
  - UIとグラフィックス
  - オーディオアプリケーションの制御
  - ユーザー向けサービス
        │
        ▼
Bluetoothホスト／システムサービス
        │
        ▼
Bluetoothプロセッサ／コントローラファームウェア
  - リンク層のタイミング制御
  - 無線スケジューリング
  - 低消費電力時の接続イベント
  - コントローラ側のプロトコル処理
        │
        ▼
Bluetooth無線部とRFフロントエンド
```

ホスト、コントローラ、アプリケーションファームウェアの分担は、SDK、スタック構成、製品要件によって異なります。ただし、Bluetooth処理に関わるCPUはメインのアプリケーションプロセッサだけではありません。Bluetoothサブシステムは独自の実行環境を持ち、無線動作の決定性を保ちながら電力効率を高めるよう設計されています。

## デバイスファミリーの違い { #device-family-differences }

SF32LBファミリーでは、デバイスのクラスによって低消費電力プロセッサの構成が異なります。使用する品種のデータシートとSDKドキュメントを必ず確認してください。

<div align="center"><em>表: デバイスファミリーの違い</em></div>

<div align="center" markdown>

| デバイスファミリー | Bluetooth機能 | 低消費電力プロセッサの役割 | 一般的な位置づけ |
|:--------------|:---------------------|:-------------------------|:--------------------|
| **SF32LB52x** | デュアルモードBluetooth（クラシックBluetooth + BLE） | LCPUはBluetoothスタックを実行し、アプリケーションコードからは利用できない | 低コストのBluetoothモジュール、オーディオアクセサリ、エントリー向けウェアラブル、コンパクトなHMI製品。 |
| **SF32LB55x** | BLE | SDKがサポートするアプリケーションタスクをLCPUで実行可能 | BLEウェアラブルや、多数のセンサーを使う低消費電力製品。 |
| **SF32LB56x** | デュアルモードBluetooth（クラシックBluetooth + BLE） | SDKがサポートするアプリケーションタスクをLCPUで実行可能 | 高機能ディスプレイ製品、ネットワーク接続型HMI、ウェアラブル機器。 |
| **SF32LB57x** | デュアルモードBluetooth（クラシックBluetooth + BLE） | LCPUがBluetoothと低消費電力タスクを担当。SDKの対応範囲を確認 | HCPU/ACPUでグラフィックスとローカル音声処理を分担する製品。 |
| **SF32LB58x** | デュアルモードBluetooth（クラシックBluetooth + BLE） | SDKがサポートするアプリケーションタスクをLCPUで実行可能 | 高度なグラフィックスやオーディオ、AI、複雑な接続機能を必要とする上位製品。 |

</div>

SiFliの[SF32LB52x HALガイド](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/hal/index.html)は、LCPUがBluetoothプロトコルスタックを実行し、ユーザーアプリケーションからは利用できないと説明しています。[SF32LB55x](https://docs.sifli.com/projects/sdk/latest/sf32lb55x/hal/index.html)、[SF32LB56x](https://docs.sifli.com/projects/sdk/latest/sf32lb56x/hal/index.html)、[SF32LB58x](https://docs.sifli.com/projects/sdk/latest/sf32lb58x/hal/index.html)のHALガイドでは、BLEやセンサー処理などの低消費電力機能をLCPUに配置する構成が説明されています。**SF32LB57x**について、SDKの[ACPUガイド](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/app_note/acpu.html)はHCPU/ACPU/LCPUの3コア構成と、BLEやセンサーデータ処理などをLCPUで実行する構成を示していますが、ユーザーが任意のタスクを追加して実行できるか、その範囲までは明記していません。各シリーズのLCPUが同じ範囲でプログラムできると考えないでください。対象品種のコア構成をデータシートで確認したうえで、使用するSDKリリースとボード構成で目的のアプリケーションタスクをLCPU上で実行できるか確認します。その組み合わせの資料がなければ、タスク配置は「未確認」とし、採用前に利用可能なメモリとスケジューリング上の制約も確認してください。

同じACPUガイドではアプリケーションコアの役割も区別されています。SF32LB57xのACPUは音声とグラフィックスを処理し、SF32LB58xでは音声DSPを担います。これらはBluetoothコントローラの処理とは別の役割です。対象ボードとSDKで利用できるタスク配置を確認してください。

表のBluetooth機能はシリーズ単位の資料を要約したものであり、すべての品種やSDKビルドで全プロファイルが使えることを保証するものではありません。SiFliの[SF32LB52xデータシート](https://downloads.sifli.com/user%20manual/DS5201-SF32LB52x-Datasheet%20V2p5.pdf)、[SF32LB55xデータシート](https://downloads.sifli.com/silicon/DS0001-SF32LB55x-Datasheet%20V1p6.pdf)、[SF32LB56xデータシート](https://downloads.sifli.com/silicon/DS0056-SF32LB56x-Datasheet%20V1p8.pdf)、[SF32LB58xデータシート](https://downloads.sifli.com/silicon/DS0058-SF32LB58x-Datasheet%20V1p6.pdf)には、表に記載したBLEまたはデュアルモード対応が示されています。SDKの[Bluetoothシグナリングテストガイド](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/app_note/bt_signaling_test_guide.html)ではBR/EDRとBLEのテストを扱い、SF32LB57xも対象に含まれています。利用する品種とSDKリリースで、プロファイル、機能、構成の対応状況を確認してください。

### アプリケーションのプログラマビリティとコントローラファームウェア { #controller-firmware-programmability }

LCPUでアプリケーションタスクを実行できても、それだけでBluetoothコントローラのソースコードにアクセスできたり、無線スタックを置き換えられたりするわけではありません。ファームウェア更新やパッチの方法、メモリやスケジューリングの制約は品種とSDKによって異なるため、対象の公式資料で確認してください。

- **低消費電力アプリケーションの開発。** 対応構成では、センサー取得、軽量な処理、システム管理をLCPUに移せます。スタックのメモリ使用量、実行時間、HCPUとの通信を見積もってください。
- **コントローラの保守とカスタマイズ。** 対象デバイスとSDKに対してベンダーが提供する更新・パッチ機構を使ってください。アプリケーションコアがプログラム可能でも、独自コントローラのソースや代替無線スタックが利用できるとは限りません。その可否はSiFliに別途確認してください。

コントローラ専用構成でも、ベンダーが提供する更新を適用できる場合があります。固定で変更不能なイメージとは限りません。変更後はBluetooth認証、相互接続性、ホストとコントローラの互換性、OTAの障害復旧を検証してください。障害復旧用のロールバックと、脆弱な旧ファームウェアの導入を防ぐセキュリティポリシーは区別して設計してください。

## BLEとデュアルモードBluetooth { #ble-and-dual-mode-bluetooth }

SF32デバイスが対応するBluetooth機能は品種によって異なり、**Bluetooth Low Energy（BLE）**のみの場合と、**クラシックBluetooth**と**BLE**の両方を使える**デュアルモードBluetooth**の場合があります。

### Bluetooth Low Energy { #bluetooth-low-energy }

BLEは低消費電力のデータ交換のために最適化されています。一般的に次のような用途で使用されます。

- フィットネスバンドとスマートウォッチ。
- 健康センサーとウェアラブル。
- スマートフォンの通知とコンパニオンアプリ。
- センサーの同期。
- ビーコンと位置情報対応デバイス。
- 低消費電力の制御・構成チャネル。

BLE通信はイベント駆動で断続的に行われるため、低消費電力Bluetoothプロセッサに適しています。

### クラシックBluetoothとデュアルモード設計 { #bluetooth-classic-and-dual-mode-designs }

デュアルモードBluetoothでは、BLEに加えてクラシックBluetoothも利用できます。次のような製品に適しています。

- Bluetoothオーディオアクセサリ。
- ワイヤレスアダプタとモジュール。
- 既存のクラシックBluetoothプロファイルとの互換性が必要な機器。
- BLEによる制御と、クラシックBluetoothによる音声やデータの通信を組み合わせる製品。

音声や従来型のプロファイルでは、より高いスループット、低いレイテンシ、厳しい共存条件が求められることがあります。そのため、デュアルモード動作はBLEのみの場合よりシステム負荷が高くなることがあります。専用Bluetoothサブシステムにより、こうした処理がメインCPUの負荷変動に影響されにくくなります。

## BluetoothオーディオとLE Audio { #bluetooth-audio-and-le-audio }

Bluetoothオーディオ製品では、無線のタイミング制御に加えて、バッファリング、コーデック処理、クロック同期、ときにはユーザーインターフェースの更新も必要になります。そのため、システム全体の設計負荷が高まります。

適切に設計されたSF32のBluetoothオーディオシステムでは、通常、次のように役割を分担します。

- Bluetoothプロセッサがコントローラ側の無線とリンクのタイミングを処理する。
- アプリケーションプロセッサが製品ロジック、UI、より高レベルのオーディオ挙動を処理する。
- I2S、PDM、ADC、DACなどのオーディオインターフェースで、サンプルデータを入出力する。
- DMAとバッファリングが、連続的なオーディオストリーミング中のCPUオーバーヘッドを削減する。

LE Audioを含む新しいBluetoothオーディオ用途では、ファームウェア構成、スタックの対応状況、コーデック、メモリ帯域幅、電力管理方針が製品の実現性を左右します。SiFliのSF32LB56xおよびSF32LB58xのデータシートにはBLE Audio対応が明記されていますが、BLE対応やデュアルモード対応だけでLE Audio対応が保証されるわけではありません。プロファイル、コーデック、SDKの実装経路は品種とSDKリリースによって異なるため、採用前に確認してください。Bluetoothプロセッサはタイミング制御の基盤を担いますが、製品全体の動作はSDKとアプリケーションの設計にも依存します。

## 低消費電力動作 { #low-power-operation }

Bluetoothサブシステムの利点が最も生きるのは、無線リンクを維持したまま、メインのアプリケーションプロセッサをスリープさせられる場合です。接続中の待機状態では、次のような必要なイベントに限ってアプリケーションプロセッサを起動すればよくなります。

- 受信した通知またはコマンド。
- 接続状態の変化。
- スケジュールされた同期タスク。
- オーディオストリームの開始または停止。
- センサーまたはユーザー入力イベント。
- ファームウェア更新またはプロビジョニング操作。

この構成なら、メインCPUを可能な限り低消費電力状態に保てます。Bluetoothプロセッサと無線部は、予定された接続イベントに合わせて起動して必要なプロトコル処理を行い、その後、システムを再び低消費電力状態へ戻します。

実際の電力プロファイルは、接続間隔、送信電力、アドバタイズの挙動、スリープモード、水晶発振子の構成、RFレイアウト、ファームウェアの方針、アプリケーションプロセッサの起動頻度に左右されます。

## ホスト、コントローラ、アプリケーションの境界 { #host-controller-and-application-boundaries }

Bluetoothソフトウェアはしばしば2つの主要なレイヤーとして説明されます。

<div align="center"><em>表: ホスト、コントローラ、アプリケーションの境界</em></div>

<div align="center" markdown>

| レイヤー | 主な責務 |
|:------|:--------------------|
| **ホスト** | プロファイル、サービス、ペアリングポリシー、アプリケーション向けAPI、より高レベルのプロトコル挙動。 |
| **コントローラ** | リンクレイヤ、無線スケジューリング、パケットタイミング、暗号化サポート、低レベルのBluetooth手順。 |

</div>

SF32システムでは、コントローラ側の責務はBluetoothプロセッサと無線サブシステムに密接に結びついています。ホスト側は、スタックアーキテクチャに応じて、アプリケーションプロセッサ上、システムファームウェア上、あるいはSDKが提供する複数のコンポーネントに分散して実行される場合があります。

アプリケーション開発者にとって最も重要な点は、Bluetoothの挙動がCPUの境界をまたぐということです。共有メモリ、プロセッサ間メッセージング、イベント、SDK APIは製品アーキテクチャの一部です。Bluetoothを、メインアプリケーションにリンクされた単なるライブラリとしてではなく、サブシステムとして扱ってください。

## アプリケーションプロセッサとの相互作用 { #interaction-with-the-application-processor }

アプリケーションプロセッサは通常、製品レベルの挙動を制御します。

- アドバタイズの開始と停止。
- 接続の作成または受け入れ。
- GATTサービスとキャラクタリスティックの管理。
- ペアリング、ボンディング、セキュリティポリシーの処理。
- スマートフォンまたはゲートウェイとのアプリケーションデータの交換。
- Bluetoothの状態が変化した際のUI状態の更新。
- オーディオストリーム、センサー、電力モードの調整。

Bluetoothプロセッサは、接続を維持するために必要な低レベルの処理を担当します。両者の間の通信は、通常SDKのAPI、イベント、キュー、またはプロセッサ間通信の仕組みによって抽象化されています。

良いアプリケーション設計は、不必要な処理のためにメインCPUを起こすことを避けます。可能な場合はイベントをバッチ処理し、適切な接続パラメータを選び、イベント駆動のコールバックが利用可能な場合は高頻度のアプリケーションポーリングを避けてください。

## RFとクロックに関する考慮事項 { #rf-and-clock-considerations }

Bluetoothプロセッサだけでは良好な無線性能を実現できません。周辺のハードウェア設計が重要です。RFレイアウト、アンテナのチューニング、クロックの精度、電源品質、量産時の較正はすべて、到達距離、感度、送信電力、接続の安定性に影響します。

重要なハードウェア上の考慮事項には次のものがあります。

- 推奨されるRFマッチングネットワークとアンテナレイアウトを使用する。
- RFトレースは短く、インピーダンスを制御し、ノイズの多い信号から十分に分離しておく。
- ハードウェア設計ガイドの水晶発振子に関する要件に従う。
- RFとクロック回路には低ノイズの電源を供給し、部品の近くにデカップリングコンデンサを配置する。
- RF較正と量産時のファームウェア書き込みに必要なテスト用接続を確保する。
- ディスプレイやストレージの高速配線、スイッチング電源の配線を、ノイズの影響を受けやすいRF経路に近づけない。

ソフトウェアチームとハードウェアチームは、Bluetoothの性能をシステムの特性として扱うべきです。ファームウェアのパラメータは、不適切なRFレイアウトや不安定なクロックを完全に補うことはできません。

## 他の処理との共存 { #coexistence-with-other-workloads }

SF32デバイスでは、グラフィックス、オーディオ、センサー、ストレージ、場合によっては外部Wi-FiとBluetoothを同時に動かします。これらのサブシステムは、電力、クロック、メモリ帯域幅、ピン、CPU時間などの資源を共有します。

共存時には、たとえば次の点に注意が必要です。

- ディスプレイのリフレッシュやPSRAMトラフィックが利用可能なメモリ帯域幅に影響すること。
- オーディオDMAとBluetoothオーディオバッファが安定したタイミングを必要とすること。
- センサー割り込みがアプリケーションプロセッサを頻繁に起こしすぎること。
- 外部Wi-Fiやその他のRFソースがBluetoothの性能に影響すること。
- 長いクリティカルセクションや割り込みの無効化が、ホスト側のBluetooth処理を遅らせること。

Bluetoothプロセッサはタイミングが乱れるリスクを抑えますが、共有資源のボトルネックをすべて解消するわけではありません。オーディオ、リッチなUI、外部無線接続を備える製品は、実際の使用を想定した最悪条件でテストしてください。

## 一般的なユースケース { #typical-use-cases }

Bluetoothプロセッサは、多くのSF32製品カテゴリの中心にあります。

- Bluetoothモジュールとシリアルアダプタ。
- エントリーレベルのスマートウォッチとフィットネスバンド。
- BLE健康センサーとウェアラブルデバイス。
- Bluetoothオーディオアクセサリ。
- スマートバッジと電子棚札。
- スマートフォンに接続されたダッシュボードとHMIデバイス。
- スマートホーム制御機器やスマートフォン連携製品。
- センサー同期とデータロギングデバイス。

適切なSF32の型番は、BLEのみでよいか、デュアルモードBluetoothが必要かに加え、オーディオ、ディスプレイ、メモリ容量、ユーザーがプログラムできる低消費電力処理の要件によって決まります。

## 実践的な設計ガイダンス { #practical-design-guidance }

SF32向けにBluetoothファームウェアを設計する際は、まず製品の接続要件を整理してください。

- 製品はBLEのみ必要か、それともデュアルモードBluetoothが必要か。
- Bluetoothオーディオは必要か。
- どのような接続間隔、レイテンシ、スループットが必要か。
- メインのアプリケーションプロセッサをどの程度の頻度でスリープから復帰させる必要があるか。
- どのイベントがシステムをDeep SleepやStandbyから起こさなければならないか。
- センサーまたはUIタスクがBluetoothのタイミングと競合しているか。
- どのようなRF到達距離と送信電力の目標が必要か。
- 量産時のファームウェアダウンロードとRF較正はどのように処理されるか。

堅牢なBluetooth設計では、Bluetoothプロセッサに加え、適切な接続パラメータ、イベント駆動型のアプリケーションコード、低消費電力状態の計画、適切なRFレイアウトを組み合わせます。

## 要点のまとめ { #key-takeaways }

- SF32LBデバイスは、無線通信のタイミングを安定して維持し、省電力で動作させるために、専用のBluetoothまたは低消費電力プロセッササブシステムを使用します。
- SF32LB52xはBluetoothコントローラ専用の低消費電力コアを使用します。SF32LB55x、SF32LB56x、SF32LB58xでは、SDKがサポートする構成に限り、LCPUにアプリケーションタスクを割り当てられます。SF32LB57xのLCPUで目的のユーザータスクを実行できるかも、対象SDKで確認してください。
- プログラム可能なLCPUでは、SDKの制約内でアプリケーション処理を実行できます。コントローラスタックのソース利用や変更の可否は別途確認し、ベンダーが提供する更新を使って変更後の動作を検証してください。
- BLEは低消費電力の接続製品向けに最適化されており、デュアルモードBluetoothはオーディオやレガシープロファイルなど、クラシックBluetoothの用途にも対応します。
- Bluetoothプロセッサは、接続、アドバタイズ、スケジュールされた無線イベントが継続する間も、メインのアプリケーションCPUがスリープするのを助けます。
- 良好なBluetooth性能は、ファームウェアアーキテクチャとハードウェア設計の両方に依存します。RFレイアウト、クロック、電源、アンテナのチューニング、較正を含みます。
- Bluetoothを、ホスト/コントローラの境界、プロセッサ間通信、電力ポリシーの判断、共有リソースの制約を持つサブシステムとして扱ってください。
