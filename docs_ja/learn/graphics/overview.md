# 概要 { #graphics-overview }

## グラフィックスのアーキテクチャを設計する { #overview }

このガイドでは、SF32デバイスで応答性の高いグラフィカルユーザーインターフェースを構築する方法を説明します。ディスプレイの選定、フレームバッファの構成、LVGLの統合、ePicassoによるハードウェアアクセラレーション、メモリ配置、画面の更新動作など、実製品に関わる設計判断を取り上げます。

SF32デバイスは、消費電力、メモリ、基板面積に厳しい制約がある小型AIoT機器やウェアラブル製品を想定しています。そうした製品では、システム要件を満たしながら、滑らかなUIを実現する必要があります。グラフィックス処理では、リソースの読み込み、ピクセルの合成、必要に応じたフレームバッファの圧縮、パネルへの出力をそれぞれ分けて考えます。各処理の役割を理解しておくと、適切な最適化を選びやすくなります。

パネルとインターフェース、フレームバッファの構成、色深度、透過、リソースの配置、画面更新の方針など、後から変更しにくいUIアーキテクチャを検討する際に活用してください。関連する各記事では、処理の個々の部分について実装方法を説明しています。

## SF32グラフィックスフロー { #sf32-graphics-flow }

グラフィックスリソースからパネルに表示されるまでの典型的な処理の流れを示します。

<div align="center"><em>図：グラフィックスリソースから表示までの流れ</em></div>

```text
画像・フォント・アニメーション素材
        │
        ▼
GraphicsToolで、対応リソースをeZipまたはeZip-A形式に変換
        │
        ▼
圧縮リソースをNOR Flash、PSRAM、NAND、またはファイルストレージに保存
        │
        ▼
必要に応じてeZipハードウェアデコーダでリソースを展開
        │
        ▼
LVGLなどのUIフレームワークとグラフィックス／ディスプレイドライバ
        │
        ├── CPUによるフォールバックレンダリング
        │
        └── ePicassoによるピクセル処理の高速化
        │
        ▼
最終的な描画結果を描画バッファまたはフレームバッファに格納
        │
        ├── 非圧縮の表示経路
        │
        └── 任意：extDMAでTurboPixel形式に圧縮
                    │
                    ▼
             TurboPixel形式のフレームバッファをPSRAMに格納
        │
        ▼
ディスプレイコントローラーがピクセルをパネルへ転送
        │
        ▼
SPI / QSPI / 8080 / RGB / MIPI DSI / EPD / JDIパネル
```

この処理経路は構成可能で、すべての製品に必須というわけではありません。eZip、ePicasso、TurboPixelや画面全体のフレームバッファを使わない構成もあります。各機能の対応状況と接続方法は、デバイス、SDK、ディスプレイインターフェース、パネル、ドライバの構成によって異なります。現行のOpenSiFli LCDCヘッダーは、`HAL_EXTDMA_MODULE_ENABLED`が有効で、チップ系列の条件を満たす場合に`LCDC_SUPPORTED_COMPRESSED_LAYER`を定義します。SF32LB52xとSF32LB57xは対象外です。また、ソースのコメントにはLCPU側では有効化されていないとの記載があります。公開SDKのLCDC機能表ではSF32LB55xの圧縮レイヤー展開が非対応とされているため、55xは実機での一連の動作が確認済みの対応ではなく、条件付きと考えてください。SDKの版、コア、ビルド設定、実機で経路全体を検証してください。詳しくは[TurboPixel](turbopixel.md#availability-in-the-sf32-family)を参照してください。

<div align="center"><em>SF32グラフィックスフローにおける役割</em></div>

<div align="center" markdown>

| ブロック | フロー内の位置 | 主な責務 | 置き換えないもの |
|:---|:---|:---|:---|
| **eZip / eZip-A** | 描画前、保存済みリソースの読み込み時 | 対応するeZip形式の静止画やアニメーション素材を可逆展開する。 | 描画処理、最終フレームバッファ、ディスプレイコントローラ。 |
| **ePicasso** | 描画・合成時 | メモリ上のピクセルに対する、対応するコピー、塗りつぶし、ブレンド、変換、合成処理を高速化する。 | リソース圧縮やパネル転送。 |
| **TurboPixel** | 描画後、対応デバイスでパネルへ出力する前 | extDMAを使って最終ビットマップを固定比率で非可逆圧縮し、PSRAMの使用量と表示読み出し帯域を抑えます。現行ヘッダーはextDMA有効時にSF32LB55x、SF32LB56x、SF32LB58x向けの圧縮レイヤー機能を定義し、SF32LB52xとSF32LB57xを除外します。コメントにはLCPU側では有効化されていないとの記載があり、公開SDK機能表では55xが非対応とされています。55xは条件付きとして扱い、コア、SDK設定、実機で経路全体を検証してください。 | 可逆のリソース圧縮やピクセル描画。 |
| **ディスプレイコントローラ** | 最終出力段階 | TurboPixel経路が有効な場合はデータを展開し、描画済みのピクセルをパネルインターフェース経由で転送する。 | eZipによるリソース展開やグラフィックス合成。 |

</div>

アプリケーションコードはUIの状態と動作を記述し、UIフレームワークはウィジェット、再描画領域、描画処理を管理します。グラフィックス／ディスプレイドライバはCPUとePicassoのどちらで処理するかを選び、バッファを調整します。ディスプレイコントローラはパネルへの転送を担当します。各機能の実装については、[ePicasso](epicasso-gpu.md)、[eZip](ezip.md)、[TurboPixel](turbopixel.md)を参照してください。

## まずディスプレイを選ぶ { #choose-the-display-first }

ディスプレイの選択は、ほぼすべてのグラフィックス上の判断に影響します。コードを最適化する前に、パネル要件を明確に定義してください。

- 解像度。
- 色深度。
- リフレッシュレート。
- インターフェースの種類。
- タッチコントローラの要件。
- バックライトやディスプレイの電源要件。
- 部分リフレッシュがサポートされているかどうか。
- パネルが内部GRAMを持つかどうか。
- 低消費電力の常時表示が必要かどうか。

小さなSPIまたはQSPI AMOLEDは、RGBパネル、MIPI DSIパネル、JDIメモリディスプレイ、EPDパネルとは非常に異なる挙動を示します。同じUIフレームワークが多くのディスプレイタイプを対象にできますが、最良のバッファ戦略とリフレッシュポリシーは変わります。

インターフェース選定、flush経路の設計、パネルの立ち上げについては、[ディスプレイコントローラ](display-controller.md)を参照してください。

## 検証済みのLVGL例から始める { #start-from-a-verified-lvgl-example }

画面を作り込む前に、製品のグラフィックス処理で最もリスクが高い部分を検証できるSDKの例を選んでください。[LVGL SDKの例](lvgl-sdk-examples.md)では、公式の基本例、デザインツール、ウィジェット、圧縮アセット、アニメーションとメディア、コンパス、ゲーム、時計インターフェースを、検証できる設計課題ごとに整理しています。製品へ移植する際に再検証が必要なボード、バージョン、ディスプレイ、メモリ、性能の前提条件も確認できます。

## フレームバッファと帯域幅の計算 { #framebuffer-and-bandwidth-calculator }

パネルやアニメーションスタイルを選ぶ前に、メモリと転送コストを見積もってください。

```text
framebuffer bytes = width x height x bytes_per_pixel
raw full-frame bandwidth = framebuffer bytes x frames_per_second
```

例:

<div align="center"><em>表: フレームバッファと帯域幅の計算</em></div>

<div align="center" markdown>

| パネル | フォーマット | 1つの完全なバッファ | 30 fpsのフルフレームトラフィック |
|:------|:-------|----------------:|--------------------------:|
| 240 x 240 | RGB565 | 約113 KiB | 約3.46 MB/s |
| 390 x 390 | RGB565 | 約297 KiB | 約9.13 MB/s |
| 454 x 454 | RGB565 | 約403 KiB | 約12.37 MB/s |
| 480 x 480 | RGB888 | 約675 KiB | 約20.74 MB/s |

</div>

バッファ容量はKiB（1,024バイト）、帯域幅は十進のMB/s（1,000,000バイト/秒）で示しています。これらは生のピクセルデータ量であり、コマンドのオーバーヘッド、アラインメント、キャッシュメンテナンス、リソースの読み出し、ブレンディング、システム内のその他のデータ転送量は含みません。BluetoothオーディオやAIを動作させたり、外部PSRAMをほかの用途で使ったりする製品では、さらに余裕を見込んでください。

## バッファを理解する { #understand-your-buffers }

UIは最終的にメモリ上のピクセルです。主なバッファタイプは次の通りです。

<div align="center"><em>表: バッファを理解する</em></div>

<div align="center" markdown>

| バッファタイプ | 目的 |
|:------------|:--------|
| **描画バッファ** | LVGLまたはグラフィックスドライバが変更された領域をレンダリングするために使用する一時領域。 |
| **フレームバッファ** | 画面全体のピクセルを保持し、ディスプレイの出力元となるメモリ。 |
| **部分フレームバッファ** | 画面全体のバッファを確保するのが難しい場合に使う、小さな領域用のバッファ。 |
| **アセットバッファ** | 画像、フォント、アイコン、またはデコードされたリソースデータ。 |
| **中間レイヤー** | ブレンディング、アニメーション、合成に使用される一時的なサーフェス。 |

</div>

画面全体のフレームバッファは扱いやすい一方、大型パネルではSRAMを使いすぎることがあります。454 × 454のRGB565バッファは412,232バイト（約412 kB、約403 KiB）で、ダブルバッファではその2倍の容量が必要です。色深度や画面サイズを上げると、必要な容量は急速に増えます。

メモリが限られている場合は、部分描画バッファを使い、変更された領域だけを更新してください。アニメーションが重要でメモリに余裕がある場合は、画面全体のバッファやダブルバッファを使うと、UIが滑らかになることがあります。

## 色深度を慎重に選ぶ { #choose-color-depth-carefully }

色深度は、視覚品質、メモリ使用量、バス帯域幅に影響します。

<div align="center"><em>表: 色深度を慎重に選ぶ</em></div>

<div align="center" markdown>

| フォーマット | ピクセルあたりのバイト数 | 備考 |
|:-------|----------------:|:------|
| **RGB565** | 2 | 組み込みUIでよく使われるバランスのよい形式。メモリと帯域幅を効率よく使える。 |
| **RGB666** | 3バイトまたはパック形式 | 色再現性は高くなるが、帯域幅も増える。 |
| **RGB888** | 3 | より高品質だが、メモリと転送コストが大きい。 |
| **RGB111 / モノクロ形式** | デバイスによる | EPD/JDIを使うアプリケーションなど、単純な表示や超低消費電力の表示に適する。 |

</div>

多くのウェアラブル製品や小型HMIでは、パネルや画質要件から高い色深度が必要でない限り、RGB565を標準候補にできます。

## 透過性、アルファ、レイヤー合成 { #transparency-alpha-and-layer-composition }

透過性は**アルファ**係数によって表現されます。これは、前景ピクセルが背景ピクセルの上に描画されるときに、どれだけ強く寄与するかを指定する値です。アルファはRGBカラーチャンネルとは独立しています。不透明なピクセルはアルファ1（または8ビットアルファチャンネルでは255）を持ち、完全に透明なピクセルはアルファ0を持ちます。

背景が完全に不透明で、前景のRGB値がストレートアルファ（乗算済みではない色値）で表され、アルファが0–1に正規化されている場合、source-over合成の各出力RGBチャンネルは次式で計算できます。この簡略式では、透明な描画先の出力アルファは求められません。

```text
output = foreground × alpha + background × (1 − alpha)
```

例えば、50%のアルファを持つアイコンのピクセルは、その色の半分を寄与させ、背景の半分を見えるままにします。この演算を繰り返すことで、背景、画像、テキスト、半透明のコントロール、影、アニメーションレイヤーといったUIの視覚的な重なりが生成されます。最終的に合成されたビットマップは、その後上記に示したフレームバッファとディスプレイコントローラの段階を経て進みます。

<div align="center"><em>表: アルファモードとその使用</em></div>

<div align="center" markdown>

| アルファモード | 意味 | 一般的な用途 | 統合上の考慮事項 |
|:-----------|:--------|:------------|:--------------------------|
| **ピクセル単位のアルファ** | 各ピクセルが独自のアルファ値を持つ。 | アンチエイリアスされたアイコンやテキスト、柔らかいエッジ、影、PNGスタイルのアセット。 | 詳細な透過性を保持できるが、ソースデータのサイズとブレンド作業が増える。 |
| **グローバルアルファ** | 1つのアルファ値がオブジェクトまたはレイヤー全体に適用される。 | 画面、ダイアログ、画像のフェード。 | 均一なフェードには効率的だが、オブジェクト内で柔らかいエッジを表現できない。 |
| **バイナリアルファ** | ピクセルは完全に可視か完全に透明かのいずれか。 | マスクと単純なグリフ。 | 複雑さは低いが、アンチエイリアスなしではエッジがギザギザに見えることがある。 |

</div>

RGB565にはアルファチャンネルが含まれていないため、通常は不透明な描画対象と最終フレームバッファに使用されます。アルファを必要とするソースアセットや中間レイヤーは、一般的にARGB8888のようなアルファチャンネルを持つフォーマット、あるいはカラー画像と別のアルファマスクの組み合わせを使用します。ドライバは、SDK、ディスプレイパス、選択したアクセラレータが実際にサポートするフォーマットを使用しなければなりません。

一般的なアルファ表現は2つあります。**ストレートアルファ**では、RGBは元の色を表し、アルファはブレンディング時に適用されます。**プリマルチプライドアルファ**では、RGBはすでにアルファが乗算されており、source-overの式は`output = premultiplied_foreground + background × (1 − alpha)`になります。この2つの表現を混在させないでください。ストレートアルファのデータをプリマルチプライドとして扱う、あるいはその逆を行うと、エッジ周りに暗いまたは明るいハローが生じます。

アルファ混合では、前景と描画先のピクセルを読み取って結果を書き込むため、単純な不透明コピーや塗りつぶしよりメモリアクセスが増えます。選択した混合処理とピクセル形式をドライバがサポートしている場合はePicassoを使い、未対応の場合に備えてCPU処理も残してください。PSRAMの帯域幅や消費電力に余裕がない場合は、画面全体にわたる半透明レイヤーを減らし、更新が必要な領域だけを描画して、中間サーフェスの使用も抑えてください。

## LVGLの統合 { #integrating-lvgl }

LVGLは、ウィジェット、スタイル、入力処理、アニメーション、再描画領域の管理、ディスプレイドライバとの接続機能を備えており、SF32デバイスで実用的なUIフレームワークです。

典型的なLVGL統合には次のものが必要です。

- ディスプレイドライバのflushコールバック。
- 1つ以上の描画バッファ。
- LVGLのタイミング用のティックソース。
- タッチ、ボタン、エンコーダ、またはジェスチャー用の入力デバイスドライバ。
- 画像とフォントのためのアセット処理。
- ePicasso用の任意のハードウェアアクセラレーションフック。

ディスプレイのflushコールバックは、描画と出力をつなぐ境界です。コントローラやDMAの動作については、[ディスプレイコントローラ](display-controller.md#controller-buffers-and-flush-paths)を参照してください。

## LVGLポーティングの判断 { #lvgl-porting-decisions }

画面の仕上げに入る前に、次のLVGL統合の詳細を確定してください。

<div align="center"><em>表: LVGLポーティングの判断</em></div>

<div align="center" markdown>

| 判断 | 好ましい方向性 |
|:---------|:--------------------|
| ティックソース | スリープへの移行と復帰をまたいでも時刻を正しく維持できる、安定したシステムtick。 |
| flushコールバック | DMAまたはディスプレイドライバから完了通知を受け取る、領域単位の転送経路。 |
| 描画バッファ数 | レイテンシとメモリ予算に応じて1つまたは2つのバッファ。 |
| 再描画領域の方針 | 小さな領域をまとめることで転送コストを下げられる場合に限り、領域を統合する。 |
| 入力デバイス | アプリのポーリングループではなく、LVGLの入力ドライバを通じて統合されたタッチ/ボタン/エンコーダ。 |
| ハードウェアアクセラレーション | SDK/ドライバがサポートする演算のみを有効化し、CPUフォールバックを維持する。 |
| キャッシュ処理 | フレームワークとドライバの境界で、共有バッファのキャッシュをclean/invalidateする。 |

</div>

適切に移植できていれば、画面側のコードは宣言的に保ちつつ、転送、同期、アクセラレーション、キャッシュの処理をドライバに任せられます。

## ePicassoアクセラレーションの利用 { #using-epicasso-acceleration }

UIで同じようなピクセル演算を大量に行う場合、ePicassoが役立ちます。代表的な処理は次のとおりです。

- 矩形の塗りつぶし。
- 画像のコピーやblit。
- アルファブレンディング。
- 画像のスケーリング。
- サポートされる画像領域の回転または変換。
- レイヤー合成。
- ドライバがサポートする場合のピクセルフォーマット変換。

移植時は、よく使う処理を高速化しつつ、未対応の処理にはCPUでの代替経路を残してください。LVGLのスタイル効果やウィジェットがすべてハードウェアで処理できるとは限りません。製品で実際に使う画面を測定して判断しましょう。

### アクセラレーションが最も役立つ場合 { #when-acceleration-helps-most }

ePicassoは通常、次のような場合に最も役立ちます。

- 大きな領域が塗りつぶされ、コピーされ、ブレンドされ、スケーリングされ、または変換される場合。
- UIが透明なアイコン、テキストマスク、影、オーバーレイ、アニメーション遷移を使用する場合。
- そうでなければCPUが各フレームの大部分をピクセルループの実行に費やすことになる場合。
- メモリ配置とピクセルフォーマットが、アクセラレータが効率的に処理できるものと一致している場合。

### アクセラレーションがあまり役立たない場合 { #when-acceleration-may-not-help-much }

次のような場合は、ハードウェアアクセラレーションの効果が限られることがあります。

- 更新される領域が非常に小さい場合。
- ボトルネックがレンダリングではなくパネル転送の帯域幅である場合。
- アセットがサポートされていないフォーマットやコストの高い変換を必要とする場合。
- バッファが十分な帯域幅のない低速メモリに配置されている場合。
- キャッシュメンテナンスのオーバーヘッドが演算を支配している場合。

## メモリ配置戦略 { #memory-placement-strategy }

グラフィックス性能は、メモリ間のデータ転送がボトルネックになることも少なくありません。用途に応じてバッファの配置を決めてください。

- 頻繁にアクセスする描画バッファは、可能であれば高速SRAMに置く。
- SRAMが不十分な場合にのみ、大きなフレームバッファをPSRAMに保持する。
- 大きな画像とフォントはFlashまたはPSRAMに保存するが、アクセスレイテンシを考慮する。
- 実行時にアセットを繰り返し変換することを避ける。
- SDKのガイダンスに従って、DMAがアクセスするバッファをアラインメントする。
- 全体のデータ転送量とデコードコストを削減できる場合は、圧縮形式やインデックスカラー形式のアセットを使う。

CPUとグラフィックス／表示ハードウェアがバッファを共有する場合は、SDKのキャッシュ管理とバッファ所有権の規則に従ってください。CPUが書いたデータをハードウェアが読む前に、該当するキャッシュラインをcleanし、必要な同期を完了させます。ハードウェアがバッファへ書く前には、CPUのダーティなキャッシュラインが後から書き戻され、結果を上書きしないよう準備します。転送完了を待ち、CPUが結果を読む前に古いキャッシュラインをinvalidateします。キャッシュラインのアラインメントと隣接データに注意し、ハードウェアが所有しているバッファは変更しないでください。SDKの対応APIを使い、cleanとinvalidateを同じ操作として扱わないでください。

部分リフレッシュ、パネル固有の挙動、段階的な立ち上げシーケンスについては、[ディスプレイコントローラ](display-controller.md)を参照してください。

## アセットの準備 { #asset-preparation }

リソースを適切に準備しておけば、コードを最適化する前からUIを軽くできます。

以下の経験則を使用してください。

- 画像の寸法を実際の画面上のサイズに合わせる。
- 大きな画像を毎フレームスケーリングすることを避ける。
- 可能な場合は複雑な影、グラデーション、背景を事前レンダリングする。
- 透過性が必要な場所でのみアルファを使用する。
- 共有のアイコンセットとフォントサブセットを優先する。
- フォントから未使用のグリフを削除する。
- 頻繁に使用されるアセットは、グラフィックスパスが効率的にサポートするフォーマットに保つ。

多言語製品では、フォントのメモリがUI予算を支配することがあります。フォントのフォールバック、グリフサブセット、テキストレイアウトを早期に計画してください。

## アニメーション戦略 { #animation-strategy }

アニメーションの滑らかさは、フレーム時間の予算、パネル帯域幅、描画コスト、消費電力に左右されます。

実践的なアプローチ:

- ユーザーが気づくものだけをアニメーション化する。
- アニメーションする領域を小さく保つ。
- アクセラレーションにうまくマッピングされる変換や不透明度の変化を優先する。
- 毎フレーム、コストの高い全画面ブラー、影、透過性の効果を避ける。
- 重要でない効果はフレームレートを下げる。
- 画面が暗くなったり、別の画面に覆われたり、非アクティブになったりしたらアニメーションを停止する。

ウェアラブルUIのすべてにデスクトップのようなアニメーションが必要なわけではありません。消費電力を増やしたりフレーム落ちを招いたりする効果を多用するより、短く分かりやすい画面遷移を少数取り入れる方が、快適に感じられることが多いでしょう。

## グラフィックス検証マトリクス { #graphics-validation-matrix }

主観的な「十分に滑らか」というチェックの代わりに、再現可能な画面を使用してください。

<div align="center"><em>表: グラフィックス検証マトリクス</em></div>

<div align="center" markdown>

| テスト画面 | 負荷をかける対象 |
|:------------|:-----------------|
| 単色塗りつぶしとカラーバー | ピクセルフォーマット、バイト順、flush経路。 |
| テキストが多い画面 | フォントメモリ、グリフキャッシュ、部分リフレッシュ。 |
| アルファ付きアイコングリッド | アルファ混合、リソース帯域幅、ePicasso経路。 |
| スクロールリスト | 再描画領域、転送帯域幅、入力レイテンシ。 |
| 画面全体の遷移 | フレーム時間の予算、ダブルバッファ、パネル帯域幅。 |
| 減光／アイドル画面 | アニメーションの停止方針、バックライト、電源管理への要求（PM vote）。 |
| 最悪条件での同時動作 | UI更新中にBluetooth、オーディオ、AIが動作。 |

</div>

画面ごとに描画時間、flush処理時間、CPU負荷、消費電力を記録してください。フレーム全体の所要時間しか測っていないと、ボトルネックがLVGL、ePicasso、メモリ、パネルインターフェースのどこにあるのか特定しにくくなります。

## グラフィックス性能のデバッグ { #debugging-graphics-performance }

UIが遅い場合は、設計を変更する前にボトルネックを特定してください。

<div align="center"><em>表: グラフィックス性能のデバッグ</em></div>

<div align="center" markdown>

| 症状 | 確認すべき可能性の高い領域 |
|:--------|:---------------------|
| 描画中のCPU使用率が高い | ハードウェアアクセラレーションの欠如、ソフトウェアピクセル演算が多すぎる、複雑なウィジェット。 |
| 描画は完了するが画面の更新が遅い | パネルインターフェースの帯域幅、flushするデータ量、ディスプレイドライバの転送経路。 |
| ティアリングやフリッカー | バッファリング戦略、同期、部分更新のタイミング。 |
| ランダムなアーティファクト | キャッシュコヒーレンシ、バッファのライフタイム、ストライド/ピクセルフォーマットの不一致。 |
| シンプルな画面は良好だがアニメーションが遅い | 画面全体の再描画、大きな領域でのアルファ混合、リソースの拡大縮小、パネル帯域幅。 |
| アイドルUI中の高消費電力 | 不要な再描画、タイマー、アニメーション、ディスプレイ/バックライトポリシー。 |

</div>

これらを個別に測定してください。

- LVGLのレンダリング時間。
- ePicassoの演算時間。
- ディスプレイのflush処理時間。
- CPU負荷。
- メモリ帯域幅への圧力。
- アクティブ、アイドル、スリープ状態での消費電力。

## よくある間違い { #common-mistakes }

早期にこれらを避けてください。後で修正するとコストが高くなります。

- 帯域幅を見積もる前にパネルインターフェースを選んでしまう。
- 小さなUI変更のたびに画面全体を再描画する。
- 性能を測定せずに、すべてのUIリソースを低速メモリに置く。
- RGB565で十分な場合にRGB888を使用してしまう。
- 大きな画像を毎フレームスケーリングしてしまう。
- ハードウェアと共有されるバッファのキャッシュメンテナンスを忘れてしまう。
- ePicassoがすべてのUI演算を自動的に高速化すると想定してしまう。
- タイマーやアニメーションを使いすぎて、CPUをスリープさせられなくなる。
- フレームレートだけを最適化し、タッチのレイテンシを無視してしまう。
- パネル初期化の検証をPCB立ち上げまで待ってしまう。

## 立ち上げチェックリスト { #bring-up-checklist }

新しいSF32グラフィックスプロジェクトを始める際は、次の項目を確認してください。

- [ ] ディスプレイの解像度、色深度、インターフェース、パネルドライバICを確認する。
- [ ] 選択したSF32デバイスが必要なディスプレイインターフェースをサポートしていることを確認する。
- [ ] フレームバッファと描画バッファのメモリ要件を見積もる。
- [ ] 全画面か部分更新か、シングルバッファかダブルバッファかを決める。
- [ ] パネルのリセット、電源、バックライト、初期化シーケンスを検証する。
- [ ] LVGLのtick、ディスプレイのflush処理、入力ドライバを実装する。
- [ ] 基本的な塗りつぶし、画像、テキスト、タッチの挙動を検証する。
- [ ] SDKとドライバがサポートする場合はePicassoアクセラレーションを有効化する。
- [ ] 共有バッファのキャッシュクリーン/無効化の挙動を検証する。
- [ ] 描画時間、flush処理時間、CPU負荷、消費電力を測定する。
- [ ] 最悪条件の画面、アニメーション、Bluetooth通信、スリープと復帰の経路をテストする。

## 要点のまとめ { #key-takeaways }

- グラフィックス設計は、ディスプレイインターフェース、解像度、色深度、リフレッシュ要件から始めてください。
- ウィジェット、再描画領域、描画、入力の管理にはLVGLなどのフレームワークを使ってください。
- 一般的なピクセル演算の高速化にはePicassoを使用しますが、CPUフォールバックパスを維持してください。
- メモリ配置とバッファ戦略は、レンダリングコードと同じくらい慎重に最適化してください。
- 帯域幅が限られたパネルや静的なウェアラブル画面には部分リフレッシュを優先してください。
- UIの性能は、CPU、ePicasso、メモリ、ディスプレイコントローラ、パネルインターフェース、タッチ入力、電源管理が関わるシステム全体の問題として捉えてください。
