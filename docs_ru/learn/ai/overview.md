# Обзор { #ai-overview }

## Обзор { #overview }

Здесь объясняется, как развернуть ИИ на устройстве SF32: выбрать устройство, подготовить модель для целевого пути выполнения, спланировать память и инференс в пределах энергетического бюджета изделия. Материал опирается на аппаратные сведения из статьи [«ИИ-ускоритель»](accelerator.md). Сначала прочитайте её, если хотите узнать о роли и ограничениях ускорителя.

SDK предоставляет ускоряемые операции через HAL **NNACC** (ускоритель нейронных сетей). Есть отдельные примеры для [HAL](https://github.com/OpenSiFli/SiFli-SDK/blob/v2.5.1/example/hal/nnacc/README_EN.md) и [драйвера RT-Thread](https://github.com/OpenSiFli/SiFli-SDK/blob/v2.5.1/example/rt_device/nnacc/README_EN.md). Они проверяют отдельную операцию свёртки depthwise (по каналам), а не полное развёртывание обученной модели. Сначала используйте их для проверки отдельной операции; среду выполнения модели, средства преобразования и реализацию каждого слоя выбирайте и проверяйте отдельно.

Приведённые ниже детали реализации относятся только к SDK v2.5.1. Ни эти детали, ни доступность NNACC на уровне семейства не гарантируют поддержку конкретной микросхемы, среды выполнения или преобразователя полных моделей, совместимость операторов, автоматический переход на CPU или вход с камеры. Проверьте всё это для точной версии и конфигурации SDK, ревизии микросхемы, среды выполнения и платы.

Эта страница пригодится тем, кто отвечает за выбор и внедрение ИИ-функции в изделие: за локальные решения устройства, допустимые затраты памяти и энергии, а также поведение модели на реальных данных датчиков. Она дополняет статью об ускорителе, где описаны аппаратные возможности и ограничения.

## Определите, какие решения устройство должно принимать самостоятельно { #define-what-the-product-needs-to-decide-locally }

Начните с задачи изделия, а не с выбора модели:

- Что устройство должно классифицировать или обнаруживать самостоятельно, без обмена данными с телефоном или облаком?
- Какие датчики подают данные для этого решения: датчики движения, аудио, биометрии, камера или их сочетание?
- Как часто нужно принимать решение и как быстро оно должно быть готово?
- Что произойдёт, если модель ошибётся? Что обходится дороже: ложное срабатывание или пропуск события?
- Нужно ли будет обновлять модель после выпуска изделия и как именно?

Ответы определяют все дальнейшие решения: размер модели, бюджет памяти, выбор устройства и возможность переводить систему в сон между запусками инференса.

## Выберите подходящее устройство SF32 { #pick-the-right-sf32-device }

Устройства семейства SF32 рассчитаны на разные сценарии ИИ-нагрузки:

<div align="center"><em>Таблица: выбор устройства SF32</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Требование | Типичный выбор |
|:-----------|:---------------|
| Нечастая классификация с небольшой вычислительной нагрузкой в изделии, оптимизированном по стоимости | SF32LB52x — небольшие модели с обработкой преимущественно на CPU. |
| Носимое BLE-устройство с базовыми задачами объединения данных датчиков | SF32LB55x |
| Более сложная обработка датчиков или мультимедиа одновременно с интерфейсом | SF32LB56x |
| ИИ на периферии как основная функция: более крупные модели, вход с камеры при поддержке выбранного устройства или жёсткое ограничение по задержке | SF32LB58x |

</div>

Таблица задаёт отправную точку для оценки, но не гарантирует, что модель поместится в память или будет работать эффективно. Для полной нагрузки проверьте память, интерфейсы датчиков, экземпляр ускорителя и поддержку SDK конкретной микросхемы. В [руководстве NNACC для SDK v2.5.1](https://github.com/OpenSiFli/SiFli-SDK/blob/v2.5.1/docs/source/en/hal/nnacc.md) указан по одному ускорителю в HCPU каждого из устройств SF32LB55x и SF32LB56x, а также по одному в HCPU и LCPU у SF32LB58x. Руководство не устанавливает, есть ли NNACC в SF32LB52x и SF32LB57x; отсутствие сведений не доказывает отсутствие ускорителя. Число экземпляров само по себе не доказывает совместимость модели или энергоэффективность. Общий контекст выбора приведён в разделе [«Позиционирование устройств семейства»](accelerator.md#device-family-positioning).

## Процесс разработки модели { #the-model-development-workflow }

Практический путь переноса модели на SF32 в целом одинаков для разных задач:

1. **Обучите или выберите модель** на рабочей станции, используя данные, похожие на те, которые датчик будет выдавать в реальном изделии. Данные из чистых лабораторных условий часто сильно отличаются от зашумлённых данных в эксплуатации.
2. **Уменьшите модель с учётом ограничений встроенной системы** — подберите архитектуру, выполните прореживание или квантование — до преобразования для конкретного ускорителя.
3. **Экспортируйте модель и сопоставьте операции** с выбранной средой инференса и с операторами, расположением данных и числовыми форматами, которые реально поддерживает целевой SDK. Наличие HAL NNACC само по себе не означает наличия преобразователя полных моделей или среды выполнения графов.
4. **Проверьте численные результаты** после преобразования и квантования; не рассчитывайте, что точность на рабочей станции сохранится без изменений.
5. **Встройте** предобработку, инференс и постобработку в прошивку: вызов модели — лишь один этап более крупного конвейера.
6. **Измерьте** задержку, использование памяти, энергопотребление и точность на реальном оборудовании, а не только в симуляции.
7. **Проверьте реалистичную совместную нагрузку**: Bluetooth, дисплей и датчики должны работать одновременно с инференсом, а не только по отдельности.

Распространённая ошибка интеграции — оптимизировать модель, не измеряя предобработку, буферизацию и постобработку. Эти этапы могут требовать столько же ресурсов, сколько ускоренный инференс, поэтому измеряйте весь путь.

## Зафиксируйте требования к среде выполнения { #define-the-runtime-contract }

До преобразования модели запишите точные требования, которым должна соответствовать прошивка во время её выполнения:

<div align="center"><em>Таблица: требования к среде выполнения</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Параметр | Что необходимо зафиксировать |
|:---------|:-----------------------------|
| Форма входных данных | Окно выборки, размер изображения, число каналов, расположение тензоров. |
| Числовой формат | Разрядность целых чисел, обработка масштаба и нулевой точки, калибровочный набор данных. |
| Набор операторов | Какие слои должны выполняться на NNACC, а для каких допустим переход на CPU. |
| Целевая задержка | Задержка всего конвейера, а не только время работы ускорителя. |
| Ограничение по памяти | Веса, активации, входные и выходные тензоры, буферы пред- и постобработки. |
| Политика обновления | Можно ли менять модель через OTA и как проверять такое обновление. |

</div>

Эти требования должны совместно проверить специалисты по ML и встроенному ПО. Если меняются формы тензоров, формат или набор операторов модели, а прошивка остаётся прежней, результатом часто становятся ухудшение точности или нестабильная задержка, а не явная ошибка сборки.

## Проверьте операторы и переходы на CPU { #operator-and-fallback-review }

До выбора модели проверьте каждый оператор, его параметры и фактический путь выполнения. Реализация на CPU или автоматический переход на неё должны быть явно предусмотрены выбранной средой; неподдерживаемая операция может вообще сделать развёртывание невозможным. Даже небольшая модель может работать медленно, если часто вызываемые слои используют CPU или многократно преобразуют расположение данных.

<div align="center"><em>Таблица: проверка операторов и переходов на CPU</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Класс операции | Значение | Действие |
|:---------------|:---------|:---------|
| Ускоряемая | Целевое устройство поддерживает прямое выполнение через NNACC. | Предпочтительно для часто выполняемых слоёв. |
| Выполняемая на CPU | Выбранная среда или прошивка предоставляет проверенную реализацию на CPU. | Измерьте затраты; используйте её только при выполнении целей всего конвейера. |
| Требующая преобразования | Нужна конвертация расположения, типа или формата данных. | Учтите её стоимость в бюджете задержки и энергопотребления. |
| Не поддерживается | Отсутствует в целевой среде выполнения. | Замените слой или измените архитектуру модели. |

</div>

Критерий успешности — не «модель запускается», а «весь конвейер обеспечивает требуемые точность, задержку, объём памяти и энергопотребление на данных с тем же распределением, с которым изделие сталкивается в реальной эксплуатации».

## Квантование и планирование памяти { #quantization-and-memory-budgeting }

Для ИИ на микроконтроллерах часто выбирают компактные квантованные модели, обычно с 8-разрядными целыми числами вместо плавающей точки. Числовой формат должен поддерживаться фактическим путём выполнения. До выбора архитектуры предусмотрите память для всех следующих компонентов, а не только для весов:

<div align="center"><em>Таблица: квантование и планирование памяти</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Потребитель памяти | Примечания |
|:-------------------|:-----------|
| Веса модели | Квантование значительно их сокращает, но они всё равно задают базовый объём. |
| Входные тензоры | Размер зависит от окна данных датчика, разрешения изображения или длины аудиокадра. |
| Промежуточные активации | Их легко недооценить; в некоторых архитектурах они занимают больше места, чем веса. |
| Выходные тензоры | Обычно невелики, но их также нужно учитывать. |
| Буферы пред- и постобработки | Фильтрация, разбиение на кадры, извлечение признаков и пороговая обработка требуют рабочей памяти. |
| Память для параллельно работающей системы | Пользовательский интерфейс, Bluetooth и аудио одновременно используют те же SRAM/PSRAM. |

</div>

Квантование может сократить затраты памяти и вычислений, но после преобразования снова проверьте точность на репрезентативных данных датчиков. Руководство SDK v2.5.1 описывает ускорение `arm_convolve_1x1_HWC_q7_fast_nonsquare`, `arm_convolve_HWC_q7_basic_nonsquare` и `arm_depthwise_separable_conv_HWC_q7_nonsquare`. В [конфигурации HAL](https://github.com/OpenSiFli/SiFli-SDK/blob/v2.5.1/drivers/Include/bf0_hal_nn_acc.h) используются 8-разрядные буферы и поля для сдвигов смещения и выходного значения. Это не доказывает прямую совместимость с нулевыми точками и поканальными масштабами произвольной современной int8-модели. Проверьте численную эквивалентность и для каждого неподдерживаемого слоя определите реализацию на CPU, преобразование либо отказ от развёртывания.

## Размещение буферов и иерархия памяти { #buffer-placement-and-the-memory-hierarchy }

Пропускная способность памяти может ограничивать ИИ даже при доступной вычислительной мощности. На SF32 с SRAM, Flash, PSRAM и кэшами инструкций/данных STAR-MC1 проверьте доступность памяти и затраты, связанные с размещением буферов:

- Размещайте часто используемые тензоры и промежуточные буферы в памяти, доступной CPU и выбранному экземпляру ускорителя, с требуемым выравниванием и расположением данных.
- Храните большие веса или редко используемые ресурсы во внешней памяти только при поддержке такого размещения выбранным путём выполнения. Если нужна копия в память, доступную ускорителю, включите её в бюджеты памяти, задержки и энергии.
- Во время передачи общим буфером должен владеть исключительно CPU либо ускоритель/DMA. До аппаратного доступа подготовьте весь диапазон, выровненный по строкам кэша: очистите строки кэша, содержащие входные данные, записанные CPU, и обработайте изменённые строки кэша выходного буфера по правилам SDK для записи со стороны устройства. Дождитесь завершения, затем инвалидируйте выходной диапазон и верните буфер CPU. Пока его использует оборудование, не изменяйте ни сам буфер, ни другие данные в тех же строках кэша.

[Реализация HAL v2.5.1](https://github.com/OpenSiFli/SiFli-SDK/blob/v2.5.1/drivers/hal/bf0_hal_nn_acc.c) проверяет, что буферы не пересекают границы адресных окон размером 1 MiB (1 048 576 байт), а входной буфер и буфер bias находятся в одном окне. Проверяйте фактически выделенные адреса, а не только общий объём свободной памяти. Блокирующий запуск ожидает завершения опросом; режим прерываний требует корректной обработки IRQ и уведомления о завершении. Проверяйте возвращаемые значения и предусмотрите восстановление после ошибок и ограниченное ожидание в приложении, не предполагая наличия тайм-аута в среде модели.

См. [STAR-MC1](../architecture/star-mc1.md#memory-system-optimization) — там описаны кэш и иерархия памяти при таком смешанном доступе.

До интеграции прошивки заполните таблицу объёма памяти, используя наихудшие, а не средние оценки:

<div align="center"><em>Таблица: расчёт объёма памяти</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Буфер | От чего зависит размер | Предпочтительное размещение |
|:------|:-----------------------|:----------------------------|
| Окно исходных данных | Частота выборки x число каналов x длительность окна x байт на отсчёт, плюс заполнение для расположения данных | Память, доступная DMA, если захват выполняет периферия. |
| Рабочая область предобработки | Фильтры, FFT/MFCC, нормализация, изменение размера или кадрирование | Быстрая SRAM, если буфер используется при каждом инференсе. |
| Веса модели | Размер квантованной модели | Flash/PSRAM, если поддерживается; в SRAM — только часто используемые части. |

| Выход и постобработка | Классы, рамки, оценки, состояние сглаживания | SRAM; объём обычно мал, но задержка важна. |
| Буферы совместной работы | Аудио, дисплей, Bluetooth, журналирование | Закладывайте одновременное использование, а не после того, как ИИ «поместится». |

</div>

Оставьте запас под стек, кучу, объекты RTOS, журналирование и OTA. Модель, помещающаяся только при отключении всех остальных подсистем, не готова к использованию в изделии.

## Соберите полный конвейер { #building-the-full-pipeline }

Ускоритель — один этап конвейера от датчика до решения. Ниже описаны три распространённых входных пути.

### Аудио и голос { #audio-and-voice }

Распознавание ключевых слов, триггеры пробуждения по голосу и классификация аудиособытий требуют захвата звука с микрофона, разбиения на кадры и извлечения признаков ещё до запуска инференса. В [обзоре аудио](../audio/overview.md) описаны захват и буферизация данных: ускоритель поможет только при эффективной записи и буферизации входящего звука.

### Движение и объединение данных датчиков { #motion-and-sensor-fusion }

Распознавание жестов, классификация активности и биометрический анализ обычно используют данные акселерометра, гироскопа или других датчиков. Сначала отдельно измерьте энергию работы датчика, захвата, предобработки и инференса, затем определите основной источник затрат. Пакетная обработка и захват по прерываниям могут сократить пробуждения, если это допускают задержка и требования к регистрации сигналов; их эффект не всегда превышает затраты модели. См. [обзор энергосбережения](../low-power/overview.md#ai-and-sensor-power-tuning).

### Камера и изображения { #camera-and-image-input }

Камера может создавать значительные затраты на захват, буферизацию, пропускную способность памяти и инференс. Реальная нагрузка зависит от разрешения, частоты кадров, работы датчика и архитектуры модели. Если точность позволяет, уменьшайте изображение или обрабатывайте область интереса. Выбирайте модель для ограничений встроенной системы, не предполагая, что модель компьютерного зрения для ПК можно развернуть без изменений.

## Планируйте инференс с учётом энергопотребления { #power-aware-inference-scheduling }

Выбирайте расписание так, чтобы обнаруживать необходимые сигналы и соблюдать время отклика. Периодический инференс оправдан, если изделию нужны регулярные решения; запуск по условиям событий полезен только тогда, когда необходимые сигналы не пропускаются.

- Где это уместно, запускайте инференс по новым полезным данным, например пороговому событию датчика или полному аудиокадру. Сохраняйте периодическую обработку, если она нужна, и после изменения запуска проверяйте пропуски событий и наихудшее время отклика.
- Если требования к задержке позволяют, обрабатывайте данные пакетами вместо множества небольших запусков инференса.
- Если устройство и SDK это поддерживают, перенесите малозатратную постоянно активную обработку данных датчиков на маломощный процессор, чтобы не будить основной процессор приложения при каждой выборке.
- Измеряйте **энергию на один инференс**, интегрируя измеренную мощность питания (напряжение питания × ток) за явно заданный интервал. В бюджет функции включайте захват, пред- и постобработку, переходы между активностью и сном. Ускорение может сократить энергию активной работы или позволить раньше заснуть, но выигрыш зависит от тока, обмена с памятью и остальной системы.

Полные рекомендации по энергопотреблению системы приведены в [обзоре энергосбережения](../low-power/overview.md). Используйте его вместе с этой статьёй для ИИ-функций, которые должны работать постоянно или почти постоянно.

## Компромисс между точностью, задержкой и энергопотреблением { #the-accuracy-latency-power-tradeoff }

Ниже приведены типичные проектные зависимости, а не неизменные правила. При выборе компромисса измеряйте реальную точность модели и энергию всего конвейера:

<div align="center"><em>Таблица: компромисс между точностью, задержкой и энергопотреблением</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Приоритет | Типичные проектные последствия |
|:----------|:--------------------------------|
| Выше точность | Модель крупнее, больше входных признаков и памяти, длиннее окно обработки. |
| Меньшая задержка | Более короткие окна захвата, ускоренное выполнение или более частые решения; проверьте влияние на точность и энергию. |
| Ниже энергопотребление | Инференс запускается реже, модель компактная, память размещена эффективно, между запусками система глубже спит. |

</div>

Перед оптимизацией решите, какое свойство важнее для изделия. Например, детектор жестов часто может пожертвовать небольшим временем отклика ради экономии батареи. Голосовой триггер обычно не должен сильно задерживаться, но при этом ложные пробуждения не должны напрасно расходовать энергию.

## Обновляйте модель и проверяйте её в эксплуатации { #model-update-and-field-validation }

Если после выпуска изделия модель может улучшаться, заранее спроектируйте поддержку её обновления:

- По возможности версионируйте модель отдельно от прошивки и храните в пакете модели требования к входным данным.
- До активации проверьте подлинность, целостность и совместимость пакета со средой выполнения и входными данными. Активация должна выдерживать прерывание обновления; при неудачной проверке запуска должен оставаться путь отката к проверенной рабочей версии.
- Храните калибровочные данные, пороги и константы постобработки вместе с версией модели, для которой они нужны.
- Собирайте достаточно статистики из эксплуатации для диагностики дрейфа данных, не сохраняя без необходимости исходные персональные данные датчиков.
- После каждого обновления модели повторяйте проверки энергопотребления и совместной работы: рост точности всё равно может ухудшить изделие, если система стала чаще выходить из сна.

## Отлаживайте производительность и точность ИИ { #debugging-ai-performance-and-accuracy }

<div align="center"><em>Таблица: отладка производительности и точности ИИ</em></div>

<div align="center" markdown style="max-width: 100%; overflow-x: auto;">

| Симптом | Вероятная причина |
|:--------|:------------------|
| Модель работает, но точность ниже, чем на рабочей станции | Несоответствие квантования или калибровки либо обучающие данные не отражают реальный шум датчиков. |
| Инференс медленнее ожидаемого | Фактическое выполнение слоёв на CPU, преобразование расположения данных, пропускная способность памяти или конкуренция при планировании. |
| Система не достигает ожидаемой глубины сна | Лишние пробуждения, активные драйверы или тактирование, блокировки управления питанием либо незавершённая операция ускорителя. |
| Отдельная функция работает, а в готовом изделии — нет | Не проверялась совместная нагрузка с одновременной активностью Bluetooth, дисплея и датчиков. |
| Высокое энергопотребление при «быстрой» модели | Измерялась задержка, а не энергия на инференс; аудиокодек или датчик оставался активным между запусками. |
| В общих буферах периодически появляются неверные данные | Подготовка строк кэша, изменённые строки, преждевременное повторное использование, отсутствие завершения или одновременное владение со стороны CPU и оборудования. |

</div>

## Типичные ошибки { #common-mistakes }

- Выбирать архитектуру модели, не проверив, какие операторы ускоряет целевая среда выполнения.
- Переносить модель для настольного компьютера вместо проектирования с учётом ограничений встроенной системы.
- Учитывать только веса модели и забывать о памяти для промежуточных активаций.
- Запускать инференс, не проверив, что частота и условия запуска обеспечивают регистрацию нужных входных сигналов и время отклика.
- Проверять точность только на чистых лабораторных данных, не учитывая реальные помехи и шумы датчиков.
- Тестировать ИИ-функцию отдельно и обнаруживать конфликты только после интеграции всего изделия.
- Оптимизировать задержку модели, игнорируя пред- и постобработку.

## Проверочный список запуска { #bring-up-checklist }

- [ ] Определите, какое локальное решение должно принимать изделие, и допустимый компромисс между задержкой, точностью и энергопотреблением.
- [ ] Выберите устройство SF32 по размеру модели и требованиям к памяти, а не только по целевой стоимости.
- [ ] Сначала соберите и проверьте полный конвейер «захват -> предобработка -> инференс -> постобработка» на минимальной тестовой модели, затем — на серийной модели.
- [ ] Преобразуйте и квантируйте реальную модель, затем проверьте точность на реалистичных данных датчиков.
- [ ] Совместно рассчитайте память для весов, входных и выходных тензоров и промежуточных активаций.
- [ ] Проверьте когерентность кэша во всех буферах, общих для CPU и ускорителя.
- [ ] Проверьте периодический или событийный запуск по требованиям к обнаружению сигналов, наихудшей задержке и измеренному бюджету энергии.
- [ ] Измерьте энергию на инференс при совместной нагрузке системы с активными Bluetooth, дисплеем и датчиками.
- [ ] Повторно проверьте точность и энергопотребление после изменения квантования, модели или расписания запусков.

## Главное { #key-takeaways }

- Начинайте с задачи изделия и данных датчиков, а не с архитектуры модели: модель — лишь этап более крупного конвейера.
- Используйте позиционирование семейств для предварительного выбора, затем проверьте конкретную микросхему, SDK, соответствие операторов, выделение памяти и совместную нагрузку.
- Планируйте память для всего конвейера: весов, тензоров, активаций и буферов пред- и постобработки, а не только для файла модели.
- Выбирайте периодический или событийный инференс без потери нужных сигналов и измеряйте энергию всей функции: скорость модели сама по себе не является результатом оценки энергопотребления.
- Проверяйте точность на реалистичных данных и тестируйте функцию при совместной нагрузке системы, а не изолированно.
