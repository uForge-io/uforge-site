# Примеры энергосбережения в SDK { #low-power-sdk-examples }

Примеры управления питанием в SiFli-SDK служат отправной точкой для измерений и интеграции, а не универсальными спецификациями тока потребления. Каждый пример рассчитан на определённое семейство микросхем, плату, схему питания, набор включённых периферийных устройств, конфигурацию прошивки и нагрузку. Сначала используйте пример, чтобы воспроизводить выбранное состояние или сценарий на целевом оборудовании, затем измерьте ток и напряжение собственного изделия в тех же условиях.

На этой странице проекты из [каталога примеров PM в SiFli-SDK](https://docs.sifli.com/projects/sdk/latest/sf32lb58x/example/pm/index.html) сгруппированы по инженерным задачам. Поддерживаемые платы, подключение питания, перемычки, настройки SDK, команды и ожидаемое поведение сверяйте с официальной страницей каждого примера.

### Уточните список целевых плат { #verify-the-board-scope }

Ниже отдельно указаны платы, перечисленные в официальном руководстве каждого примера, и цели из текущей конфигурации сборки SiFli-SDK для GCC. Наличие платы в матрице означает, что проект настроен как цель сборки; оно не подтверждает, что опубликованные значения энергопотребления измерялись на этой плате. Если названия плат в руководстве и идентификаторы целей сборки различаются, не считайте их взаимозаменяемыми без проверки соответствия плат. Ссылки на конфигурацию ведут в текущую ветку `main`; если используется другая ревизия SDK, перед выбором цели `scons --board` сверяйтесь с файлом `build_config_gcc.yaml` именно из этой рабочей копии SDK. Чтобы воспроизвести измерение, используйте описанную в руководстве аппаратную конфигурацию. Название семейства в URL документации не означает автоматическую поддержку всех чипов и плат этого семейства.

- **PM Example** ([исходный код SDK](https://github.com/OpenSiFli/SiFli-SDK/tree/main/example/pm/classical)): в руководстве перечислены `sf32lb56-devkit-lcd_n16r12n1`, `eh-lb551`, `sf32lb52-lcd_n16r8` и `sf32lb58-lcd_n16r64n4`. В текущей конфигурации GCC для проекта используется идентификатор `sf32lb56-lcd_n16r12n1` (он отличается от указанного в руководстве `sf32lb56-devkit-lcd_n16r12n1`), а также `eh-lb551`, `sf32lb52-lcd_n16r8` и `sf32lb58-lcd_n16r64n4`; дополнительно включена цель `sf32lb52-core_n16r16`. Не считайте разные идентификаторы взаимозаменяемыми без проверки соответствия плат.
- **GPIO Power Consumption Test** ([исходный код SDK](https://github.com/OpenSiFli/SiFli-SDK/tree/main/example/pm/gpio)): и руководство, и текущая конфигурация GCC указывают `sf32lb52-core_n16r16`.
- **Processor Power Consumption Test** ([исходный код SDK](https://github.com/OpenSiFli/SiFli-SDK/tree/main/example/pm/coremark)): в руководстве перечислены `eh-lb551`, `eh-lb555`, `ec-lb583`, `ec-lb587`, `eh-lb561`, `eh-lb563` и `eh-lb523`. Списки плат из руководства и целей `default_boards` не совпадают по названиям один к одному. Сверьте соответствие для используемой ревизии SDK, а не определяйте его по названию. Наличие цели сборки также не означает, что опубликованные измерения охватывают каждую плату из набора.

В отдельной записи для этого проекта также присутствуют `sf32lb56-wlan-core_a128r12n1` и `sf32lb56-wlan-core_n16r12n1`. Не подменяйте названия плат из руководства идентификаторами целей сборки, не проверив соответствие.
- **AMOLED Power Consumption Test** ([исходный код SDK](https://github.com/OpenSiFli/SiFli-SDK/tree/main/example/pm/AMOLED)): и руководство, и текущая конфигурация GCC указывают `sf32lb52-core_n16r16`.

## Измеряйте на правильной электрической границе { #measure-at-the-right-electrical-boundary }

Сравнивайте осциллограмму потребления изделия с примером SDK только при одинаковых электрических границах измерения. Например, примеры GPIO и включения экрана при поднятии запястья описывают подключение питания и перестановку перемычек на конкретных платах. Питание от USB, подключённый отладчик, преобразователь UART, зарядная цепь или модуль дисплея могут существенно изменить результат.

Для каждого измерения зафиксируйте:

1. Точку подключения питания и все линии, на которые подано напряжение.
2. Напряжение питания, режим дискретизации и диапазон прибора для измерения тока.
3. Подключённые внешние устройства, подтягивающие резисторы, кабели и интерфейсы отладки.
4. Ревизию прошивки, имя платы, конфигурацию `menuconfig` и настройку отладки PM.
5. Переход состояния или нагрузку, которым соответствует каждый участок осциллограммы.

Измеряйте напряжение вместе с током, чтобы определять мощность и энергию, а не только ток потребления. В статье [«Измерение и проверка энергопотребления»](measurement-and-validation.md) подробно описана проверка отдельных компонентов, сценариев и суточного профиля.

## Базовые тесты PM, GPIO и процессора { #baseline-pm-gpio-and-processor-tests }

Начните с [базового примера PM](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/example/pm/classical/README.html), чтобы проверить нужный режим сна и источники пробуждения до добавления нагрузки изделия. Зафиксируйте запрошенное состояние PM и проверьте, в какое состояние система действительно переходит. Если система не переходит в запрошенное глубокое состояние сна, сначала проверьте конфигурацию и то, какой компонент управляет запросами PM. Не переходите к тонкой настройке параметров, пока не устраните эту причину.

**Тест энергопотребления GPIO** помогает разобраться, почему интерфейс, который кажется неактивным, повышает ток в состоянии покоя. В описанном сценарии устройство периодически просыпается для чтения GPIO, что позволяет отделить ток сна от затрат на пробуждение и операции I/O. Для изделия проверка должна быть шире: внутренние и внешние подтяжки, состояния high-Z, связи между доменами питания, выводы выключенных периферийных устройств, состояния после сброса и возможные пути утечки через ESD-защиту и цепи обратного питания. Даже логически корректный сигнал может создавать ток утечки.

**Тест энергопотребления процессора** разделяет принципиально разные условия: вычисления CPU, простой цикл, отключение, пробуждение по таймеру и от вывода. Он позволяет оценить затраты на активные вычисления и проверить пробуждение, но сам по себе не определяет энергопотребление приложения. Перед включением результатов в энергетический бюджет замените бенчмарк или цикл репрезентативной нагрузкой прошивки.

## Сценарии Bluetooth и дисплея { #bluetooth-and-display-scenarios }

Используйте отдельные проекты [Передача рекламных пакетов BLE и установление соединения](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/example/pm/ble/README.html) и [BLE/BT](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/example/pm/bt/README.html), чтобы получить воспроизводимые радиосценарии до настройки параметров соединения в приложении. Готовое изделие всё равно нужно измерять с его собственными параметрами передачи рекламных пакетов и соединения, вторым устройством, радиоокружением, антенной и обработчиками обратного вызова. Если приложение будит основной CPU при каждом радиособытии, хорошие результаты измерений самого соединения могут не сохраниться на уровне изделия.

Примеры для дисплеев помогают проверить другие решения:

- **Тест энергопотребления AMOLED** сравнивает сон с выключенным экраном и политику постоянно включённого экрана. Переключение режимов и оценки автономности из источника относятся к описанным плате, панели, яркости, временам обновления и модели использования, а не к любому изделию с AMOLED.
- [Тест энергопотребления JDI](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/example/pm/jdi/README.html) даёт аналогичную исходную точку для конкретной платформы с JDI-дисплеем.
- [Руководство по примеру GUI_PM](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/example/pm/gui_pm/README.html) связывает жизненный цикл интерфейса пользователя с поведением PM.
- [Сценарий обновления экрана](https://docs.sifli.com/projects/sdk/latest/en/sf32lb52x/example/pm/lcd_refresh/README.html) рассматривает нагрузку от обновления дисплея.

Эти примеры помогают ответить на вопрос: какие события действительно требуют изменения пикселей и какую часть панели нужно обновлять? Статьи [«Обзор графики»](../graphics/overview.md) и [«Контроллер дисплея»](../graphics/display-controller.md) помогут выбрать организацию буферов и политику частичного обновления.

## Включение экрана при поднятии запястья как полный сценарий { #raise-to-wake-as-a-complete-scenario }

Проект **«Включение экрана при поднятии запястья»** особенно полезен тем, что объединяет опрос датчика, распознавание жеста, пробуждение дисплея, ограниченное время взаимодействия и возврат в сон. Это пример сценария изделия, а не отдельного состояния.

Оценки автономности в исходном примере зависят от указанной ёмкости аккумулятора, числа пробуждений, времени работы экрана, датчика, интервала опроса, платы и измеренных токов. При адаптации сохраните структуру расчёта: измерьте состояние с включённым экраном и с выключенным экраном, задайте число событий в сутки и рассчитайте суммарную суточную энергию. Затем подставьте собственные значения изделия вместо копирования чисел из примера.

Разобранный цикл моделирования и измерений приведён в статье [«Профилирование энергопотребления умных часов»](smartwatch-power-profiling.md).
