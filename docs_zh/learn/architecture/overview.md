# 概览 { #architecture-overview }

SF32 各器件在处理器、内存资源和专用硬件配置上存在差异。根据具体型号集成的模块，设计可将时序敏感或需要常开运行的任务交由专用子系统硬件处理。若型号配备适用的加速器，也可由硬件执行图形处理等任务。本节围绕五项工程决策组织架构内容：应用代码在哪里运行；代码和缓冲区放在哪里；哪些工作应交由无线控制器处理；何时适合使用专用任务引擎；以及所选器件是否具备所需的架构模块和接口。

## 实用决策原则 { #practical-decision-rule }

建议按以下顺序进行架构决策：

1. 在应用固件中实现产品逻辑、用户界面行为、应用策略和常规驱动。结合所选器件和实际工作负载，参考 STAR-MC1 文章评估处理器与缓存行为，不要认为通用基准测试结果就能代表实际应用性能。
2. 尽早确定代码和数据的存放位置。将延迟要求严格的代码和数据放在合适的内存层级，并在确定 UI、音频、AI 或通信工作负载之前，估算所需的外部存储容量、接口带宽和功耗预算。
3. 将蓝牙控制器的时序要求与产品级策略分开考虑。蓝牙处理器文章说明了控制器、主机和应用的职责划分，以及需要协同设计的 RF 和低功耗环节。
4. 面对自定义外设任务，先确认现有定时器、DMA 路径、UART、SPI、I2C、音频、显示或蓝牙功能是否已经满足需求。仅当任务确实有严格的时序要求，或难以通过这些标准模块合理实现时，才在 SF32LB57x 上考虑 PTM。

对于每一项决策，在假设某个架构模块存在或可由用户编程前，都必须核实所选器件已公开的能力。SF32LB57x 硬件设计指南记载了 1 个 PTM 模块、共 16 个通道；在设计中依赖 PTM 前，也要确认目标器件的文档明确支持该模块。
